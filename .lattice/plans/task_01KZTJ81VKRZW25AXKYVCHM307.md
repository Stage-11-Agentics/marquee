## What exists and what does not — verified, not assumed

**Exists:** `migrations/0005_task_cancellation_webhooks.sql` creates
`webhook_endpoints` (id, event_id, url with a `https://` CHECK, `secret_hash`,
`events_json` constrained to six event names, `enabled`, `created_at`,
`last_delivery_at`) and `webhook_deliveries` (id, endpoint_id, event_type, payload,
status `queued|delivered|failed`, attempts, response_code, error, created_at,
delivered_at). `src/db/schema.ts` carries the row types. `src/index.ts:43` declares
a `WEBHOOK_QUEUE: Queue<unknown>` binding.

**Does not exist:** any route, any API handler, any UI. Nothing produces to
`WEBHOOK_QUEUE`. `git grep -l webhook src/` returns only schema, the queue binding,
delivery-health, mail-failure, observability, reset-demo, and two unrelated route
files. The six event names are enforced in SQL by a table that nothing writes.

So this is **not** "restore a regressed page" — the surface was advertised and
never built.

## THE TRAP — read before writing code

MRQ-106 (PR #75) removed `/settings/webhooks` from `docs/ROUTES.md` as a route
claim that "shipped false", and left an assertion in
`tests/node/wave-0-sweep.MRQ-106.test.mjs`:

```js
assert.doesNotMatch(map, /`\/settings\/webhooks`/);
```

**That assertion will fail when you succeed, and that is correct.** `docs/ROUTES.md`
is generated by `npm run check:routes` from the route sources, so the path can only
appear there by actually being served. When your route exists, regenerate the map
(`npm run check:routes -- --write`) and **update that stale assertion to require the
path rather than forbid it.** Do not work around it, do not skip the test, and do
not hand-edit `ROUTES.md`.

## Scope — deliberately bounded for the deadline

**1. CRUD API** for `webhook_endpoints`, scoped to an event: create, list, update
(url, events, enabled), delete. Enforce the `https://`-only and six-event-name
constraints at the Zod layer too, so the user gets a real error rather than a SQL
CHECK failure.

**2. Secret handling.** Store `secret_hash`, never the secret. Show the secret
exactly once at creation. **Reuse the existing shown-once panel pattern in
`src/ui/settings/ApiTokensPage.tsx` — do not build a second secret UI.**

**3. Test-send.** A per-endpoint action that signs and POSTs a sample payload,
then writes a real `webhook_deliveries` row. This is what proves signing works
end to end without the full dispatcher.

**4. Delivery log.** Read `webhook_deliveries` per endpoint — status, response
code, error, timestamp. The index `idx_webhook_deliveries_endpoint_created` exists
for exactly this query.

**5. The route.** Register `/settings/webhooks` in
`src/ui/shell/route-table.ts` alongside `/settings/api`, `/settings/venues`,
`/settings/tasks`. Follow those siblings exactly — same group, same shape.

## Explicitly OUT of scope

**Do not build the event-triggered dispatcher.** Wiring
`submission.created` / `status_changed` / `evaluation.completed` /
`speaker_task.completed` / `agenda.published` / `speaker.confirmed` into
`WEBHOOK_QUEUE` and draining it is a much larger job than the hours remaining.
Test-send proves the signing path; the automatic trigger is a follow-up. **Say so
plainly in the PR body** — do not let the surface imply live event delivery it does
not have. An honest, working CRUD + test-send + log beats a half-wired dispatcher,
and this product's philosophy is that a screen must never claim more than it does.
