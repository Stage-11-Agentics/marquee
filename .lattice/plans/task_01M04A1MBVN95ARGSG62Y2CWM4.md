# MRQ-248: The mirror builds its own tables: empty-base provisioning and template adoption

WHY. An organizer pointing Marquee at a fresh Airtable base hits a dead end: connect refuses with "Airtable returned no tables for this base." (src/jobs/mirror/actions.ts:134-136) — they must hand-build three correctly-shaped tables first, with no stated shape. The sibling failure: a base made from an Airtable template, mapped via the three dropdowns, passes mapping cleanly and then fails hours later as Stuck: N with an opaque provider error in mirror_state.last_error (consumer.ts:97-111) — a clear form-time error deferred into an unreadable drain-time one. Making the base shaped right is chase work the system should do. PHILOSOPHY 2/5 (the mirror is a genuine surface; their base stays theirs).

SCOPE. All on the existing Settings → Airtable door (src/ui/settings/AirtablePage.tsx) — no new screen. (a) EMPTY BASE: the refusal becomes the offer — a primary "Create the three tables for me" provisions Submissions, Speaker tasks, People with the declared columns, re-reads the schema, lands on mapping with all three pre-selected, and reports per table ("Created Submissions · 28 columns"). The empty base becomes the easiest path. (b) TEMPLATE/PARTIAL BASE: mapping keeps the dropdowns (the name heuristic at AirtablePage.tsx:69-79 becomes a pre-selection fallback); on confirm an adopt pass adds ONLY missing columns and reports honestly ("Adopted Speakers · added marquee_id, title · kept your 4 extra columns"). Organizer-added columns are never touched. (c) WRONG-SHAPED TABLE: the failure moves from runtime to the form — a column whose existing type conflicts with what the mirror writes is named at mapping time, field-level, in plain language; no webhook registers and the mirror stays off. CRITICAL: because writes set typecast: false (transport.ts:202), the diff MUST compare types as well as names — a name-only diff adopts a base that then hard-fails every PATCH. (d) READ-ONLY TOKEN (no schema.bases:write): connect still succeeds against an already-correct base; against one needing changes it refuses with a sentence naming the scope — raw provider text never reaches the organizer. (e) AGENT PATH: cli/marquee.mjs mirror verbs (:402-413) gain --provision + the same adopt report, or the agent-native path is strictly worse than the UI (PHILOSOPHY 3).

DATA MODEL. No migration — mirror_state.airtable_table_id already persists per-table ids (keep id-addressing; it survives renames). Code: new src/jobs/mirror/schema.ts holding MIRROR_TABLE_SCHEMA (name AND Airtable type per column, derived from the three field maps in records.ts:68-158 — the declaration that has no home today) + ensureMirrorSchema(transport, tables) → {createdTables, adoptedColumns, conflicts}. AirtableTransport (transport.ts:31-56) grows createTable + createField — implemented in the fetch transport, in FakeAirtableTransport (mutating its in-memory tables so tests assert WHICH columns were added), AND in rateLimitedAirtableTransport (transport.ts:78-112 — a hand-written passthrough where a forgotten method silently escapes the base-wide 4 req/s budget with capacity 1; the easiest mistake in this work, and it gets its own AC). connectMirror/mapMirror grow the provision branch and the pre-webhook column diff; response schemas widen (watch check:api parity). docs/GETTING-STARTED.md:174-200 must start naming token scopes at all (today it names none); schema.bases:write documented as required-for-provisioning, optional otherwise.

CONTRACT FOLD (executing agent): SPEC §3.9 amendment + US/AC mint at consolidation; re-check next-mint (AC-314 as of 2026-08-15).

AC DRAFTS. Empty base offers provisioning; accepting creates exactly the three tables per MIRROR_TABLE_SCHEMA and lands on mapping pre-selected, report naming each table. Adopting adds only missing columns (incl. marquee_id), organizer columns untouched — asserted via the fake transport's exact createField calls. Type-conflict refuses at mapping, field named; no webhook, mirror stays off. schema.bases:write absent: connects against a correct base; refuses with the scope named otherwise. Rate wrapper covers both new methods (a provision through the wrapper consumes the serialized budget). AC-310's discipline extends to the new branches: no test inserts mirror_state as a fixture — the connect flow is the only on-switch. CLI provisions an empty base end to end.

VALIDATION. Hermetic against the fake transport (the MRQ-223 discipline — no credential, no network); one live smoke against a real scratch base when available.

COORDINATION. Disjoint from MRQ-239 (inbound hardening: inbound.ts + cascade/decisions.ts) except the AirtableTransport interface and the MRQ-223 test fixture (tests/integration/mirror-connect-inbound.MRQ-223.test.ts:34-38 — this ticket adds empty-base and template-base fixtures beside it). Whichever merges second rebases over a small interface diff; noted in both.

CUT LINE. Smallest: empty-base provisioning at connect + column-presence validation at mapping (deletes both dead ends). Complete: type-aware adopt pass with per-column report, scope degradation, CLI parity, GETTING-STARTED scopes.

### Design and implementation sequence

1. Establish one schema authority in src/jobs/mirror/schema.ts. 2. Extend AirtableTransport with createTable and createField. 3. Make schema mutation explicit at both lifecycle boundaries. Add a provision intent to connect/map requests and CLI flags. On an empty base, an explicit provision request creates exactly Submissions, Speaker tasks, and People from MIRROR_TABLE_SCHEMA, re-reads the schema, and returns the per-table creation report plus the selected tables. On a non-empty base, mapping's explicit adopt/provision action runs the same two-phase schema check and creates only missing fields, including marquee_id. A mapping against an already-correct base performs no schema write and succeeds without schema.bases:write. A mapping that needs mutation without that Airtable scope returns a safe sentence naming schema.bases:write; provider response text never reaches the organizer.

   The UI's first connection attempt remains a verification/read path. When the base is empty it exposes the primary Create the three tables for me action, which retries with the explicit provision intent. Mapping confirmation is the explicit adoption action and reports Created/Adopted per table, added fields, and kept organizer columns. The CLI mirrors this shape with mirror connect --provision for empty-base creation and mirror map --provision for explicit adoption; without the flag, correct bases still work and bases needing changes receive the same safe scope refusal. If the orchestrator review selects a different flag placement, amend this plan before implementation.
