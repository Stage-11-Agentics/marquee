## 3. Issues

CI run 31843696164 (sha `584d5cbb`) fails `npm test` with status `fail` — load-invariant per the repo's gate vocabulary, so it blocks. Three tests break, all from adding the `org-settings` row to the Organization sidebar group:
- `tests/unit/people.MRQ-131.test.ts:252` — expects the organization group's sidebar ids to be exactly `["people", "sourcing"]`; now `["people", "sourcing", "org-settings"]`.
- `tests/unit/route-table.test.ts` (MRQ-203 group contract) — expects the group labels `["People CRM", "Outreach"]`; now also `"Settings"`.

**Fix:** in this branch, add `"org-settings": "settings"` to the swyxy `navLabels` in `src/ui/shell/register.ts`, and update the two group-structure contract tests to the ruled structure that now includes the ⚙ Settings row — legitimate contract evolution, since SPEC Amendment 21 §5 and ruling O1 explicitly add the row to the group. **[MAJOR] src/lib/auth/instance-claim.ts:286-290 — Invite exchange binds the session to an existing person by unverified typed email (privilege escalation)**
`exchangeInstanceLink` looks up `people WHERE org_id = ? AND email = ?` using the email the *recipient typed*, and when a row exists it creates the session on that person (`createSession({ personId: person.id, … })`). Authorization resolves entirely from `memberships WHERE person_id = ?` (`scope-resolution.ts:124`), and `role_hint` is only a hint. So the holder of *any* live invite — including a conference-scoped `reviewer` or `ops` one — who types an existing owner's email (typically public or guessable) receives a session carrying the owner's full memberships. Nothing verifies they control that inbox; the flow is mail-independent by design. This mechanism predates the ticket, but it only becomes an escalation now: under Amendment 19 every invite legitimately minted `owner`, so there was nothing to escalate to. Amendment 21's whole point — "the recipient confirms who they are and never what they may do" (AC-296) — is bypassable, and "a conference-scoped invite never yields an organization-wide seat" holds for the *membership row* while the *session* still yields org-wide authority. The design doc names email-keyed auth as an identity edge (`sequence/org-settings-design.md` §merge/email-change) but doesn't cover this door. The AC-296 tests cover a `role` in the exchange body being ignored, but not an existing organizer's email being typed.
**Fix:** in `exchangeInstanceLink`, when the typed email matches an existing person who already holds any non-`speaker` membership, refuse the exchange (inert/401 with copy like "this email already has access — sign in instead") rather than minting a session as them. Binding to an existing membership-less CRM row (the day-of volunteer already imported as a person) stays allowed — that's the desirable case. Add a test: mint a `reviewer` invite, exchange with the owner's email, assert no session lands on the owner person. If instead this is judged acceptable for an invite-only instance, it must be an explicit documented ruling in Amendment 21's guardrails, not silence.

**[MINOR] src/lib/auth/short-code.ts:71-73 — Digit suffix has modulo bias**
`Uint16Array` mod 10,000: 65,536 % 10,000 ≠ 0, so suffixes 0000–5535 are ~17% likelier than 5536–9999. The entropy loss is negligible (~0.01 bits) and nothing is exploitable behind a rate-limited single-use credential — but the file's own header argues the wordlist is exactly 256 *so that a byte selects with no modulo bias*, and the suffix two lines later doesn't hold itself to the same standard, which invites a future reader to trust a property that isn't there.
**Fix:** rejection-sample (draw `Uint16`, retry on ≥ 60,000, mod 10,000), or note the accepted bias in the comment.

**[MINOR] src/routes/org-settings.routes.ts:54 — `comms_reply_to` accepts any string**
Validated only as `trim().max(320)`. A non-address here ("reply to the programme team") is inherited by every future conference's mail voice and discovered as bounced or malformed reply-to headers months later — exactly the delayed-failure shape the neighbouring timezone check exists to prevent.
**Fix:** validate the shape (`z.string().email()` or an equivalent light check) while keeping `null` for unset.

**[MINOR] src/routes/org-people.routes.ts:92-98 — Invite list, mint-echo, and revoke are not scoped by `invite_org_id`**
This ticket makes the *exchange* multi-org-correct (`invite_org_id` decides where the seat lands, and `readOrganization` pointedly refuses "first row wins"), but `listOrganizerInvites` still returns every pending `org_invite` on the instance, and `revokeOrganizerInvite` will revoke any of them by id. On an instance holding more than one organization row, one org's admins see and can kill another org's pending invites. Pre-existing single-org assumption, but the branch half-fixes it, and the column to finish the job now exists.
**Fix:** filter both queries with `AND (l.invite_org_id = ? OR l.invite_org_id IS NULL)` bound to `auth.orgId`.

**[MINOR] src/ui/settings/EventSettings.tsx:317 — Stale comment describes a removed card**
The comment "Organizers are instance-level people, surfaced here because this is where an organizer already looks…" survives the removal of the `OrganizersCard` beneath it and now argues for a card that isn't there.
**Fix:** delete the comment (its argument moved to `/org/organizers`).

## 4. Positive Observations

- **The statements-not-calls revocation module is the right architecture.** `access-revocation.ts` returning prepared statements so every caller composes one `DB.batch()` makes atomicity structural rather than disciplined, and the ownership predicates on `revokeCreatedTokensStatement` (`org_id` + `created_by` both bound) make client-supplied token ids safe by construction — and there's a test (`tok_not_theirs`) proving it.
- **Per-arm revocation tests that prove their fixtures first.** Each AC-298 arm asserts the fixture is live *before* acting (one unexpired link beside a spent and an expired one; three live tokens), so a test that would pass vacuously against an empty fixture cannot. The spent link keeping its original `used_at` — never re-dating history — is the kind of assertion most suites never think to write.
- **The short-code design is careful where it counts:** second credential on the same single-use row, hashed at rest with a test proving the raw code isn't stored, spending either form kills both, malformed input refused before it ever reaches a hash, and the 256-word list length asserted at module load rather than trusted.
- **Seat-off-the-consumed-row discipline** in `exchangeInstanceLink`, with pre-Amendment-21 rows explicitly defaulted to what they already meant (no silent demotion of invites in flight), scope validated against the minting org at mint *and* exchange, and a deleted conference narrowing the seat to nothing rather than silently to the whole org.
- **Null-means-unsaid is enforced end-to-end** — nullable columns, `.strict().partial()` PATCH with a literal-allowlist SQL builder, `cacheOrgDefaultTheme` removing the key rather than writing `day`, and the AC-295 unit test importing `index.html?raw` to assert the pre-paint script reads the same three layers in the same order — duplication asserted, not trusted.
- **The contract fold is genuinely consistent:** Amendment 21 in all three documents, the shared-numbering note (Amendment 22 / AC-302+ reserved for MRQ-204) recorded in each, the bodyless-invite default change (owner → program_lead) stated in SPEC and enforced by an updated AC-282 test, and the FK-count bump to 107 correctly reflecting the mid-build addition of `invite_org_id` (the plan's 106 was stale, not the code).
- Route registration by `*.routes.ts` glob meant zero wiring risk for the two new modules, and `docs/ROUTES.md` was updated in the same change.
