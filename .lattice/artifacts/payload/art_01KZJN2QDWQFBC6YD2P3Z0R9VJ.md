# Plan Review: MRQ-14 — Uploads: presign, verify, and serve (cycle 2)

## 1. Verdict

**FAIL (plan-level)**

## 2. Summary

Reviewed the revised MRQ-14 plan — body plus the thirteen-item **Plan-Review Cycle 1 Resolutions (AUTHORITATIVE)** block — against the ticket description, `SPEC.md` §2.1/§3.3/§3.4/§4.2/§5.4/§5.5, `EVALUATION.md` §1.1/§1.2/§1.4 and the AC-52/146–148/231/232 rows, `BUILDPLAN.md` §4/§7/§10 and its line-353 duplicate-claim amendment, `.lattice/orchestration/ticket-map.md`, and the actual merged-candidate code in `Marquee-worktrees/mrq-1-platform-skeleton` and `mrq-2-schema`. Cycle 1's thirteen findings are all triaged, and eleven of them are closed correctly and with real reasoning — the Turnstile split (res. 3), the AC-52 ownership swap (res. 6), the client-module relocation plus bundle scan (res. 10), and the `If-None-Match` defense-in-depth with a named CopyObject fallback (res. 8) are all the right calls, argued from the contract rather than asserted.

The key concern is that **resolution 2 — one of the two "PRE-RESUME SCHEMA FOLD REQUIRED" items being filed against MRQ-2 *right now* — is built on a table that does not exist.** There is no `drafts` table in `0001_init.sql`; SPEC models a draft as a `submissions` row with `status='draft'` (`SPEC.md:190`, `:198-199`, `:210`), and submit is a status transition, not a row creation. Resolution 2 asks MRQ-2 to add a `draft_file` owner keyed to `drafts.id` and instructs the implementer to build a submit-time re-parenting transaction that the data model neither needs nor permits. Because that fold is being cut into a *merged* migration before MRQ-14 resumes, getting it wrong is exactly the expensive-later mistake cycle 1 correctly argued to avoid. A second blocker sits underneath it: the stated `0002` fallback for both schema folds is not mechanically available in SQLite.

Everything below is small and mostly editorial — this is one more short revision pass, not a re-plan.

## 3. Issues

```
**[CRITICAL] Cycle-1 Resolutions #2 — `draft_file` (`owner_id = drafts.id`) references a table that does not exist, and the re-parenting transaction contradicts the draft model**
The resolution reads: "Add `draft_file` (`owner_id = drafts.id`) and `submission_file` (`owner_id = submissions.id`) to the attachment owner CHECK while MRQ-2 is open. Public field uploads attach to the durable draft before submission; the submit transaction re-parents them to the created submission..." There is no `drafts` table. `mrq-2-schema/migrations/0001_init.sql` declares 44 tables (`organizations` … `event_settings`) and none of them is `drafts`. A Marquee draft *is* a `submissions` row: `submissions.status` defaults to `'draft'` with `'draft'` in its CHECK (`0001_init.sql:326-332`), `resume_token_hash` and `last_saved_at` live on that same row (`:344`, `:343`), and `SPEC.md:210` is explicit — "**Draft queue is derived, not copied** (AC-249): `status='draft'` plus `last_saved_at`…". `POST /api/v1/public/forms/:slug/drafts` (`SPEC.md:363`) creates that submission row and issues the resume token; submit flips `status` to `'submitted'` and stamps `submitted_at`. There is no "created submission" to re-parent into.

Two consequences, both expensive. (a) MRQ-2 is being asked to bake a `draft_file` value into a migration that will merge and then need a second migration to remove. (b) MRQ-15 (Tier A, AC-30–AC-42) would be handed an instruction to write a re-parenting transaction that, if implemented, breaks `resume_token_hash` continuity across submit and desynchronizes the derived draft queue (AC-249) — the failure mode is a resumed draft (`SPEC.md:439`, "restoring all completed values **and files**") losing its files at exactly the moment the AC says they must survive.
**Recommendation:** Collapse resolution 2 to a single owner value. Amend the MRQ-2 fold to add **`submission_file` only** (`owner_id = submissions.id`), valid from `status='draft'` onward — the submission row already exists before any public presign, because Turnstile-gated draft creation (`SPEC.md:42`, `:445`) precedes it. Delete the `draft_file` value and the entire re-parenting mechanic; submit is a status transition and the attachment rows are untouched by it. Note that `attachments.owner_id` carries no FK (`0001_init.sql:112`), so the polymorphic pointer is already legal against `submissions.id`. Keep `person_headshot`, `task_upload`, `event_logo` as they are; MRQ-14's implemented owner set then becomes those three plus `submission_file` (four, not five — this also supersedes the count in resolution 13).
```

```
**[CRITICAL] Cycle-1 Resolutions #1 and #2 — the stated `0002` fallback is not expressible in SQLite, and `attachments` has two inbound foreign keys**
Both folds say: "If MRQ-2 merges without this fold, MRQ-14 must add `migrations/0002_mrq_14_attachments.sql`." The two changes are (i) `sha256 TEXT NOT NULL` → nullable (`0001_init.sql:118`) and (ii) widening the `owner_type` CHECK (`:109-111`). SQLite's `ALTER TABLE` supports only `ADD COLUMN`, `RENAME`, and `DROP COLUMN` — it cannot alter a column's nullability and cannot add, drop, or modify a CHECK constraint. The fallback therefore requires the full 12-step table rebuild, not a one-line ALTER. That rebuild is genuinely hazardous here: two tables hold foreign keys into `attachments` — `people.headshot_attachment_id TEXT REFERENCES attachments(id)` (`:132`, plus index `:736`) and `calendar_invites.attachment_id TEXT REFERENCES attachments(id)` (`:602`) — and SQLite's `ALTER TABLE … RENAME TO` rewrites FK clauses in *other* tables unless `legacy_alter_table` is set, so a naive rename-copy-drop silently repoints both. Presenting this as a routine `0002` under BUILDPLAN §7's "every later change is its own `000N_<ticket>.sql`" understates it by a wide margin, and an implementer who reaches for it under time pressure at the end of a 5-hour ticket is reaching for the most dangerous file in the repo.

Note the asymmetry: `ALTER TABLE attachments ADD COLUMN r2_etag TEXT;` **is** legal and safe in a `0002`. Only the NOT NULL removal and the CHECK widening need the rebuild.
**Recommendation:** Promote both folds from "preferred, with fallback" to **blocking pre-resume prerequisites**. MRQ-2 is still open (worktree `mrq-2-schema` at `c22e1bd`, unmerged), so this costs nothing today. State plainly in the plan: MRQ-14 does not resume until `attachments.sha256` is nullable, `r2_etag TEXT` exists, and `submission_file` is in the CHECK — all inside `0001_init.sql` via MRQ-2. If the Orchestrator judges the fold cannot land, the plan must then spell out the rebuild procedure explicitly (`PRAGMA foreign_keys=OFF`, create `attachments_new`, copy, drop, rename, re-create `idx_people_headshot_attachment`, `PRAGMA foreign_key_check`) and MRQ-14's estimate must absorb it — do not leave a 12-step rebuild hiding behind the phrase "must add `migrations/0002`."
```

```
**[MAJOR] Cycle-1 Resolutions #5 / serve.ts — origin isolation is specified in one direction only, so the media host also serves the whole app and API**
Resolution 5 is right about the SPA-fallback trap and the `run_worker_first` fix. But every isolation rule in the plan points the same way: "The app host returns 404 for the media route", "requires an app-host request for the same media path to 404", "media GET is accepted only on `MEDIA_PUBLIC_ORIGIN`, never the app host." Nothing says what the *media* host does with every other path. With one Worker, one `assets` block, and `not_found_handling: "single-page-application"` (`mrq-1-platform-skeleton/wrangler.jsonc:16-30`), adding `media.marquee.stage11.dev` as a second custom domain means that hostname serves the full SPA at `/` and the entire `/api/v1/*` surface — the `assets` and `routes` config is Worker-wide, not per-host. The separate origin is then not separate from the application at all: an uploaded file served at the media origin sits same-origin with the API. That matters more here than usual, because the plan's stated non-goal leans the whole no-AV-scanning argument on origin separation ("separate origin + `Content-Disposition: attachment` + `nosniff`, documented as an extension point"). Host-scoped session cookies (trap 15, no `Domain` attribute) limit the blast radius to unauthenticated and bearer-token calls, which is why this is major rather than critical — but it hollows out the defense the non-goal is resting on.
**Recommendation:** Add an explicit rule to `serve.ts` and to resolution 5: on `MEDIA_PUBLIC_ORIGIN`, the Worker returns a typed JSON 404 for **everything except** the media path — no SPA, no `/api/*`, no health route — and that check runs before routing. Add it to the local validation matrix as its own assertion (request `/` and `/api/v1/events` with the media Host header; both must 404 with a non-HTML content type), symmetrical to the app-host-404 assertion already specified.
```

```
**[MODERATE] Cycle-1 Resolutions #8 — a per-serve HEAD doubles R2 operations on a graded-speed path, and is avoidable**
The ETag defense-in-depth is a good call, but the mechanism as written is "every media serve HEAD-compares the current ETag before streaming" — an extra R2 round trip on every image and file read, on a product where speed is a graded feature (R7) and headshots appear in the chase board and review queue. `MEDIA.get(key)` already returns the object's `etag`/`httpEtag` on the same call that produces the body, so the comparison costs nothing extra if it is made against the single `get`.
**Recommendation:** Restate resolution 8 as: serving performs one `MEDIA.get(key)` and fail-closes if the returned `etag` does not match the `r2_etag` recorded at completion. Same guarantee, one operation. Keep the HEAD form only where there is genuinely no body fetch (e.g. the deletion-confirmation assertion, which already uses `MEDIA.head(key) === null` correctly).
```

MRQ-16 then codes against `variantUrl(attachment, 'card')` and is insulated from the verdict either way. Also add the media-host `/cdn-cgi/image/*` pass-through question as an explicit MRQ-57 probe, not an implied one.

## 4. Positive Observations

- **The resolutions block is the right instrument, used well.** Thirteen findings, each named with its severity, an explicit accept, and — critically — a statement of *which prior sentence it overrides* ("ORIGINAL LIFECYCLE STEP 1 OVERRIDDEN", "ORIGINAL OWNERSHIP BULLET OVERRIDDEN"). A revised plan that leaves the superseded text in place and silently contradicts it is the normal failure mode here; this one declares precedence in its header and then honors it. That is a genuinely reviewable document.

- **Resolution 3 is the standout call.** Cycle 1 argued the Turnstile split from SPEC and the plan not only accepted it but reasoned forward to the consequence — the named AC-231 test now covers missing/invalid/replayed Turnstile *on the public route* plus missing-auth and out-of-scope ownership *on the authenticated routes*, and explicitly does not assert that an authenticated route needs a challenge. It closed the contract question and adjusted the test that would otherwise have re-opened it. It also correctly routed the ruling to MRQ-49/A-7 as decided rather than re-litigable.

- **Resolution 8 turned a "prove it later" into layered defense.** Keeping `If-None-Match: *` as primary, adding the completion-observed `r2_etag` as an independent local check, naming the exact fallback if MRQ-57 finds the conditional unsupported (staging key → server-side `CopyObject` → never-presigned final key), and explicitly refusing "expiry and randomness alone" as a fallback — that is a plan that has thought about what happens when its own bet loses. Cycle 1 asked for a fallback; it got a better one than the one suggested.

- **Resolution 1 correctly separates two things that look like one.** "Do not store an MD5-shaped ETag in a column named `sha256`, and do not trust a client-declared digest" is exactly the distinction that would otherwise have been quietly collapsed by an implementer under deadline pressure, producing a column whose name lies about its contents for the life of the repo.

- **Resolution 11 refuses the silent cut.** Naming the two staged commits, stating that the sweep and variants remain in scope because downstream tickets consume them, and instructing the implementer to *stop and ask for a split* rather than ship an uncalled sweep or a fake variant contract — that is the correct response to an estimate risk, and it is the opposite of what usually happens at hour five.

- **Resolution 12 protects a shared budget from a local decision.** Byte-array fixtures constructed in-test, no committed binaries, and an explicit requirement to prove `npm test` stays ≤30s from a cold invocation — this defends the fleet-wide inner-loop clock and keeps borrowed sample documents out of a repo that is about to be published under an open licence. Two problems, one rule.
