## 2. Summary

The plan (a verbatim adoption of the task description, which is unusually plan-shaped: exact files, exact code, a named reference implementation, a ratio for the hard limit, and a test property) proposes giving `check-seed.mjs` the budget/hard-limit split that `run-test.mjs` already has. ## 3. Issues

**[MAJOR] "The audit" / item 4 — The audit table misses a second stopwatch red inside `speed.ts`, so item 4's written decision could be scoped too narrowly**
The plan claims "grepping every script in `scripts/checks/` for a status-from-elapsed comparison returns exactly two files." That grep evidently covered only `.mjs` files. `scripts/checks/speed.ts:358-371` contains a third instance: `harnessFail = checkSpeedElapsedMs > checkSpeedBudgetMs`, OR'd directly into status — `status: classified.shouldFail || harnessFail ? "fail" : "pass"`. This is not the R7 graded-measurement path the plan's table excuses as "arguably by design"; it is the harness's *own wall clock* (exactly the cost that moves with machine load) turning status red, i.e. the identical bug shape being fixed in `check-seed.mjs`. An implementer following item 4 literally ("decide `check:speed` deliberately") could write a header decision covering only the `classifySpeedMeasurements` path and leave `harnessFail` undocumented — reproducing the exact "inheritance rather than decision" the ticket exists to end.
**Recommendation:** Extend item 4's scope explicitly: the written decision in `check-speed.mjs` must cover both red paths — the graded measurement classifier *and* the `harnessFail` stopwatch at `speed.ts:358` — either defending each or applying the warn split to the harness path. No behavior change is required by this review; the decision just has to name both.

**[MAJOR] Item 5 — The property test is infeasible as a real run under the 45s suite budget; the plan doesn't say how it will actually be written**
"An over-budget `check:seed` run exits 0" cannot be tested by running the real script over budget: the real run boots wrangler and takes ~30s on a healthy box, which alone would consume two-thirds of the suite's 45s budget (and CLAUDE.md makes a slow default suite a defect, not a cost). "A hang still exits 1" is worse — the hard limit will be ~390s. The status/exitCode derivation is currently inline in the script, unexported and untestable. The plan's own item 5 therefore forces a small refactor it never names.
**Recommendation:** Extract the verdict derivation into a pure, exported helper (following the existing `speed-budgets.mjs` precedent — classification logic in a testable module, the script as a thin caller): something like `deriveSeedOutcome({ elapsedMs, budgetMs, hardLimitMs, timedOut })` returning `{ status, verdict, exitCode }`. Pin the property with fast unit tests over that helper (over-budget → `pass-over-budget`/exit 0/`verdict: "warn"`; past hard limit → exit 1). Do not write an integration test that actually waits.

**[MINOR] Item 2 — `run-test.mjs`'s hard-limit mechanism does not transplant; the in-process design needs a deliberate choice**
`run-test.mjs` enforces its hard limit by SIGTERM-ing *spawned children* (`run-test.mjs:52-56`). `check-seed.mjs` is a single in-process script whose long pole is `await withLocalRuntime(...)`. The ratio (13× → ~390s) transplants; the mechanism doesn't. A watchdog `setTimeout` works here (the event loop stays alive while the await hangs), but it must be `unref()`'d or explicitly cleared so a healthy run doesn't hold the process open, and the timeout path must set `status: "timeout"` (matching `run-test.mjs:102`'s vocabulary) and exit 1 — including cleaning up the wrangler child that `withLocalRuntime` owns, or the killed run leaves an orphan on the contended box everyone is fighting for.
**Recommendation:** Specify the mechanism: an unref'd/cleared watchdog timer (or an abort signal threaded into `withLocalRuntime`), status `"timeout"` on fire, exit 1, and confirmation that the local runtime's child process is torn down on the timeout path.

**[MINOR] Item 3 — The `verdict` mapping should be stated, not just guarded**
Item 3 correctly flags that `recordSpeedHarness` receives `verdict: result.status` (`check-seed.mjs:65`), but stops at "make sure it keeps receiving a meaningful verdict." The codebase already has the answer: `run-test.mjs:88` and `pr-gate.mjs:67` both record `verdict: overBudget ? "warn" : "pass"`, and `speed-budgets.mjs:30-32` classifies exactly the vocabulary `pass`/`warn`/`fail`/`missing`. I confirmed nothing programmatically consumes `harness.check_seed.verdict` today (`command.mjs:108` only preserves it across `check:speed` runs), so the risk is history legibility, not breakage.
**Recommendation:** Record `verdict: "warn"` on over-budget and `"pass"` otherwise, matching the two sibling scripts exactly — never write a `status` string (`pass-over-budget`) into the `verdict` field.
