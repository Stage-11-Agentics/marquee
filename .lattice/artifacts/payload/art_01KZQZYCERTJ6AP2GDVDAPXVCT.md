# Plan Review: MRQ-35 — Category routing

## 1. Verdict

**FAIL (plan-level)**

One issue is mechanically fatal: the plan's AC-claims manifest as written will trip the `duplicate-owner` error in `trace-ac-core.mjs` (AC-234 is already owned by MRQ-5), which fails `npm run trace:ac` and the mandatory `pr-gate` the plan itself lists as a gate. A one-line fix, but the plan text commits to the failing form. Two further majors — a public-facing 422 semantic that turns admin committee composition into a speaker-visible dead end, and an unspecified rollback mechanism for resumed drafts — need explicit resolution before implementation, because they interact: resolving the first largely dissolves the second.

## 2. Summary

I reviewed the MRQ-35 plan against the live codebase: `scripts/checks/trace-ac-core.mjs`, the existing claim manifests, `migrations/0001_init.sql` (routing_rules, submissions.applied_rule_id, round_assignments), `src/lib/reviewer-scope.ts`, `src/routes/evaluation.routes.ts` (distributeAssignments), `src/routes/public-form.routes.ts` (handlePublicSubmission), `src/routes/review.routes.ts`, `src/routes/submission-record.routes.ts`, and SPEC §3.10 / EVALUATION AC rows. The plan is strong on decomposition, file mapping, and AC decoding — the schema and seams it names all exist as described. The key concerns are the claim-manifest collision and a committee fail-closed semantic that the plan justifies as an isolation requirement but which the existing `authorizeReviewerScope` read-time seam already covers.

## 3. Issues

**[CRITICAL] Tests and evidence — `owns: ["AC-234"]` collides with MRQ-5 and fails the trace gate**
The plan specifies `tests/ac-claims/MRQ-35.json` with `owns: ["AC-135", "AC-136", "AC-137", "AC-234"]`. But `tests/ac-claims/MRQ-5.json` already declares `"owns": ["AC-3", "AC-234", "AC-245", "AC-249"]`, and `scripts/checks/trace-ac-core.mjs:77` emits a hard `duplicate-owner` error when two claims own the same AC. `npm run trace:ac` and the mandatory `npm run pr-gate -- --ticket MRQ-35` — both listed as gates in this very plan — will fail as written. The established pattern for a ticket that covers-but-doesn't-own an AC is `exercises` (see `tests/ac-claims/MRQ-13.json`: `"exercises": ["AC-33", "AC-234"]`).
**Recommendation:** Change the manifest spec to `owns: ["AC-135", "AC-136", "AC-137"]`, `exercises: ["AC-234"]`. AC-tagged test titles may still include AC-234 — title coverage is counted independently of ownership.

**[MAJOR] Objective / step 3 / tests — rejecting the public submission (422) because of committee composition is a product decision the plan asserts without a supporting AC, and its isolation justification is weaker than stated**
The plan commits to failing the speaker-facing public submit with a 422 (and full rollback) whenever the routed committee contains *any* member whose track scope doesn't intersect the carried tracks. Two problems. First, the isolation argument: read-time exposure is already sealed — `authorizeReviewerScope` (`src/lib/reviewer-scope.ts:81`, the single AC-246 path) independently requires the requesting reviewer's own track intersection on every queue/record/evaluation access, even for committee assignments, and the queue query in `review.routes.ts` goes through the same membership joins. A `committee_id` pool row does not expose the submission to an out-of-scope member. Second, the product consequence: committees are explicitly heterogeneous ("reviewers review one or more tracks," SPEC §3.10 / Amendment 2), so any committee whose members' scopes aren't a superset of every submission's tracks would hard-fail public submissions routed to it. That converts an ordinary admin configuration into a speaker-visible dead end — against the Tier A zero-dead-ends walkthrough rubric — and the natural error message ("reviewer is outside the submission's track scope") leaks internal reviewer-scope semantics onto a public surface. The existing fail-closed precedent the plan leans on (`distributeAssignments` in `evaluation.routes.ts`) 422s an *admin* who can fix scopes, not a speaker who cannot. No AC in AC-135–137/AC-234 requires rejecting the submission when routing can't complete.
**Recommendation:** Decide the refusal semantic explicitly, and prefer: accept the submission (it is the speaker's data), and fail closed on the *routing side only* — either skip stamping/assignment entirely (unrouted submission, visible in the default pipeline) or stamp the rule and write only the pool row that the read-time seam already scopes. If the delegator believes full-submit rejection is genuinely required, the plan must cite the binding constraint and acknowledge the walkthrough-loop consequence. The isolation test should then assert what actually matters: an out-of-scope committee member cannot *see or touch* the routed submission through queue/record/evaluation paths, with `round_assignments` assertions adjusted to the chosen semantic.

**[MAJOR] Step 3 — "roll back the staged submission-side changes on refusal (including resumed drafts)" names an outcome, not a mechanism, and the mechanism is genuinely hard**
`handlePublicSubmission` is a sequence of non-transactional D1 statements. A resumed draft is mutated in place — `status` flips to `submitted`, and title/abstract/answers/tracks/participants/attachments are replaced — before any point at which `reviewerCanBeAssignedToSubmission` could run (the helper reads persisted `submission_tracks` rows, so candidate rows must exist first, which is presumably what "stage only the candidate submission/track state" means). Restoring a resumed draft's prior state has no existing snapshot mechanism; hand-rolled restore of six tables is exactly where a partial-failure bug hides. There is also a latent tension with the plan's own constraint "do not add a second reviewer-scope predicate": the clean alternative — validating against candidate track IDs before any write — requires either a parameterized variant of the single helper or a second predicate.
**Recommendation:** If the 422 semantic is dropped per the previous issue, this problem mostly disappears — say so and simplify step 3. If any pre-commit validation remains, specify the mechanism: either (a) extend `reviewerCanBeAssignedToSubmission` with an optional candidate-track-IDs parameter (an extension of the single predicate, not a second one — note this in the plan so the constraint isn't misread), validated before any submission write; or (b) snapshot-and-restore with the exact tables enumerated. Do not leave "roll back" as a to-be-discovered detail.

**[MINOR] Step 2/3 — "materializes the committee pool assignment" is ambiguous about representation, and a `committee_id` row would be the schema shape's first writer**
`round_assignments` supports both shapes (per-reviewer row, or `committee_id` pool row — CHECK at `migrations/0001_init.sql:510`), and the read paths (`review.routes.ts`, `authorizeReviewerScope`) handle committee rows — but the only existing writer, `distributeAssignments`, materializes per-reviewer rows with `committee_id` NULL. The plan's test language ("the expected committee/round/submission row") implies a single committee row.
**Recommendation:** State the representation explicitly. A single `committee_id` pool row is the better fit for routing (one row, read-time scoping does the rest), but since this ticket would be that shape's first producer, the test should also assert a scoped committee member actually sees the submission in their queue — proving the row is live, not just present.

**[MINOR] Step 2 — "resolves the event-owned active round" has no schema backing for "active"**
`evaluation_rounds` has no active flag — only `position`, `opens_at`/`closes_at`, and the parent plan's `status`. "Active round" is undefined, and the plan doesn't say what happens when a committee-target rule's plan has no rounds or isn't open (the admin distribution path requires `plan.status = 'open'`).
**Recommendation:** Define the resolution rule (e.g., lowest-`position` round of the targeted/open plan) and the no-round / closed-plan behavior — which should follow whatever refusal semantic the major issue above settles on.

## 4. Positive Observations

- **The AC decoding is exactly right.** Any-carried-track matching (never only `primary_track_id`), submission-time application, and named provenance on the record are all pulled correctly from AC-135–137/AC-234, and the `{field, op, value}` / `{plan_id|committee_id}` rule shape matches SPEC §3.10 verbatim. The `position, id` evaluation order even matches the seeded index (`idx_routing_rules_event_enabled_position`).
- **The file map is accurate.** Every named artifact exists — `applied_rule_id` is already in the schema and the record response (`submission-record.routes.ts:385` returns `routing: { rule_id }`), so step 4 is correctly scoped as a name-join extension rather than new plumbing.
- **The single-predicate discipline is the right instinct.** Routing through `reviewerCanBeAssignedToSubmission` rather than minting a parallel scope check honors the AC-246 seam; the issues above are about *where* and *when* it's applied, not the choice of predicate.
- **The test plan is unusually concrete** — first-position selection, secondary-track-only matching, vendor routing away from mainstage, positive scoped control with count assertions, and the full gate list including `pr-gate`. The claim-manifest issue aside, the evidence design is what plans should look like.
- **Non-goals are well-drawn** — no migration, no admin/import routing creep, no contract-document edits, public-repo hygiene.
