# Plan Review: MRQ-60

## 1. Verdict

**FAIL (plan-level)**

## 2. Summary

I reviewed the MRQ-60 plan against the actual state of `src/api/runtime.ts`, `src/api/router.ts`, `src/lib/auth/*`, the MRQ-9 sibling worktree, and the repo's test/check conventions. The sequencing (wait for MRQ-9, self-review, resolver-only PR fallback) is sound and the security intent is correct, but the plan has real gaps in exactly the areas that determine whether the merge is safe: it doesn't say what happens to the plain-Hono endpoints the task description explicitly calls out ("~7 handler schemas"), it doesn't specify how `authorize()` becomes event-aware given its current two-argument signature, and it glosses over a real semantic mismatch between the grant-enum model `Principal` uses and the role-rank model `AuthContext`/`roleForEvent` uses. On a guardrail-adjacent, pre-public-deploy-blocking ticket, these need to be nailed down before implementation, not discovered mid-build.

## 3. Issues

**[MAJOR] Auth model and runtime wiring, step 4 — "the ~7 handler schemas" are plain-Hono endpoints outside the manifest/schema system, and the plan doesn't say what happens to them**
The task description's "~7 handler schemas that assume an unauthenticated context" almost certainly refers to `src/routes/auth.endpoints.ts` (5 handlers) and `src/routes/admin-ops.endpoints.ts` (2 handlers) — there are no 7 schema-bearing routes anywhere in the tree (the manifest currently registers only 2, both intentionally public). These 7 are plain `Hono<{ Bindings: Env }>()` apps mounted *ahead of* the manifest in `src/index.ts`, with hand-rolled JSON error envelopes (not `ApiError.toEnvelope`), and they already do their own auth via `authHasRole`/`getAuth` reading MRQ-3's Hono variable `auth` (set by `authMiddleware`, which is non-rejecting and always calls `next()`). They are not part of `ApiEnv`/`ApiVariables`/`ApiBindings` at all. Step 4 talks about reconciling "API environment/bindings and handler context types" — language that describes the manifest-routed `ApiEnv` path, not these plain-Hono handlers. The plan needs to explicitly state: do these 7 endpoints (including `reset-demo`, a sensitive admin op) get migrated onto `Principal`/`CredentialResolver`, or do they keep their existing `AuthContext`-based checks permanently, with the two auth mechanisms coexisting by design? Right now it's ambiguous, and this ambiguity sits directly on top of the task's explicit scope line.
**Recommendation:** Add an explicit sub-step naming the 7 files/handlers, and state the decision (migrate vs. leave as-is with justification). If left as-is, say so and explain why two parallel auth mechanisms are acceptable post-MRQ-60.

**[MAJOR] Auth model and runtime wiring, step 3 — "make API authorization event-aware" doesn't specify how `authorize()` gets an `eventId`**
`authorize()` in `src/api/router.ts` currently takes only `(policy, principal)` — no `eventId` parameter — and the credential-resolution → rate-limit → authorize step in the pipeline runs before request validation. Making authorization "event-aware" per route means threading a per-route `eventId` (presumably a path param, but the manifest's routes may name it differently, or the ID may need to come from a body/query on some routes) into `authorize()` before schema validation has run. The plan states the goal but not the mechanism: where does `eventId` come from at that point in the pipeline, how is it declared per-route (a new field on the route policy?), and what happens for routes where the resource's event scope isn't a simple path param.
**Recommendation:** Specify the mechanism — e.g., a `policy.auth.eventIdParam` convention read via `c.req.param(...)` before validation — and confirm it against at least one concrete route (the re-gated submissions route) before implementation starts.

**[MAJOR] Auth model and runtime wiring, steps 1–3 — grant-enum vs. role-rank semantics aren't reconciled**
`Principal`'s token arm carries `grants: readonly ApiGrant[]` (a fixed 7-value capability enum from `src/api/grants.ts`), and `authorize()` presumably checks against that enum. `AuthContext`'s session arm has no grants at all — `roleForEvent`/`authHasRole` instead resolve a membership **role** (speaker < … < owner, via `ROLE_RANK`) and rank-compare it to a required role. These are two different authorization vocabularies: capability strings vs. a role hierarchy. Step 3 says "session admin authority derives from `roleForEvent`," but doesn't say how a resolved role becomes something `authorize()`'s grant-based check can consume for session principals, or how bearer-token `scopes.permissions` (today interpreted as role names by `authHasRole`, not grants) maps onto `ApiGrant`. This is the crux of the reconciliation work step 1 promises but doesn't detail.
**Recommendation:** Add a concrete mapping table (or a documented decision to keep `authorize()` polymorphic — role-rank check for sessions, grant check for tokens) as part of step 1, before code is written.

**[MAJOR] Tests and the MRQ-9 handoff, step 6 — re-gating the submissions route breaks more than "MRQ-9's current-public test"**
The MRQ-9 worktree's `tests/integration/api/submissions-list.test.ts` has a shared `request()` helper (lines 80-84) that hard-asserts `response.status === 200` on *every* test in the file, not just the explicit "public until MRQ-60" guard test. Flipping the route to authenticated-admin will fail the entire file, not the one named test. Step 6 as written ("convert MRQ-9's current-public test to assert unauthenticated 401/403...") undercounts the actual scope of the required test rewrite and risks the implementer being surprised by a wall of unrelated-looking failures, or worse, patching only the named test and leaving the rest red.
**Recommendation:** Reword step 6 to say the shared test helper/fixture in that file needs rewriting (e.g., an authenticated-admin credential threaded through `request()`), not just the one guard test.

**[MINOR] Ground truth and sequencing — MRQ-9 worktree state description is stale**
The plan states MRQ-9's files "are currently untracked in the sibling MRQ-9 worktree." As of this review, they're committed on branch `mrq-9-submissions` at `af9c9f9` with a clean working tree (not pushed to the Forgejo remote). This doesn't change the plan's correct decision to wait for MRQ-9 to merge before doing the re-gate, but the stale factual premise should be corrected so a reader doesn't infer the wrong current state.
**Recommendation:** Update the sequencing note to reflect committed-but-unmerged/unpushed status.

**[MINOR] Verification and delivery, step 7 — some redundancy between listed checks and `pr-gate`**
`npm run pr-gate -- --ticket MRQ-60` already runs `npm test` and `trace:ac --scope=merged --ticket=...` internally as two of its seven checks. Running them again standalone isn't wrong, just partially redundant with what step 7 already lists as separate commands. Not a defect, just worth tightening so the step doesn't read as if `pr-gate` is a lighter-weight final gate than it is.
**Recommendation:** Note that `pr-gate` subsumes `npm test`/`trace:ac`, and that the standalone runs are for faster iteration during development, not an extra independent gate.

## 4. Positive Observations

- The dependency handling is careful and correct: the plan explicitly refuses to copy/edit MRQ-9's in-progress work, defers the re-gate until after MRQ-9 merges, and has a real fallback (resolver-only PR with the hole explicitly still open) rather than papering over a missing dependency.
- Security discipline is strong throughout: explicit requirements to preserve immediate D1 session revocation, never log credential material, fail closed when the resolver is absent, assert *no leaked submission data* (not just status codes) in the new tests, and prove cross-event reviewer isolation at the API layer (AC-214 reaching a new surface) — all correctly scoped to what this ticket is actually for.
- Correctly follows the project's established ruling (per `run-state.md`) that MRQ-60 must not create a `tests/ac-claims/MRQ-60.json` entry, and says so explicitly in the PR-body requirement — this is an easy thing to get wrong (and would have broken `trace:ac`'s scope check) and the plan gets it right.
- The self-review/PASS-artifact/validation steps are concrete about naming the exact final HEAD, which matters given headless plan/code review is suspended for this run and the ticket is flagged guardrail-adjacent for orchestrator hand-review.
