# Plan Review: MRQ-204 — Delete conference (contract-first cascade, Danger zone, type-name confirm)

### 1. Verdict

**FAIL (plan-level)** — a targeted revision, not a rethink. The plan's shape is right (contract → seam → parity → UI → coverage → validation) and matches §T2 closely. But it asserts audit semantics that the current schema makes unimplementable without a migration the plan never mentions, and it hardcodes AC/US ID ranges that have no recorded allocation and can collide with a sibling ticket. Both are exactly the kind of thing contract-first exists to settle *before* build; fixing them in the plan costs two sentences now versus a stalled build or a re-minted contract later.

### 2. Summary

Reviewed the six-step delivery plan for MRQ-204 against the ticket text (`sequence/sidebar-fold-tickets.md` §T2), SPEC Amendment 19, the shipped `remove-demo` implementation (`src/lib/reset-demo/remove-demo.ts`), the init migration, and the v1.15 prototype modal. The plan is well-decomposed and demonstrates real codebase awareness (the `attachments.event_id` wart, the Next-mint rebase conflict, both confirm-gate arms, D1 batch transactionality). The key concern: **"audit log survives, deletion audited with actor" collides head-on with `audit_log.event_id TEXT NOT NULL REFERENCES events(id)`** — with no `ON DELETE` clause anywhere in the schema and tests running on real workerd D1 (which enforces FKs), the contracted behavior cannot ship without a schema decision the plan doesn't contain.

### 3. Issues

**[CRITICAL] Step 2 (Shared deletion seam) — Audit-survival contract is unimplementable against the current schema**
The contract (task description and §T2) requires that the audit log *survives* the deletion and that the deletion itself is *audited with actor*. But `migrations/0001_init.sql:701–712` declares `audit_log.event_id TEXT NOT NULL REFERENCES events(id)`, there are zero `ON DELETE` clauses in any migration, and the test suite runs under `@cloudflare/vitest-pool-workers` — real D1, which enforces foreign keys. Deleting the `events` row while any audit row references it fails the FK constraint; so does the deletion-audit row itself the moment its parent event vanishes. The shipped `remove-demo` dodges this precisely by *deleting* audit rows (`DELETE FROM audit_log WHERE event_id IN (…)` is in `REMOVE_DEMO_STATEMENTS`) — which is also why "unify rather than fork" is not a pure refactor (see next issue). The plan's step 2 says "preserve organization rows and audit history … record the deletion audit row with actor inside the same transaction" as if this were free, and no step includes a migration.
**Recommendation:** Add an explicit contract decision + migration to step 1/2: most likely a migration softening `audit_log.event_id` (nullable, or a plain TEXT column with the FK dropped, preserving the id for history), with the SPEC amendment stating the post-delete referential semantics of surviving audit rows. Decide it in the SPEC amendment, not mid-build — it changes what AC-30x can promise.

**[MAJOR] Step 1 (Contract) — AC-302–AC-307 / US-90–US-91 are speculative allocations with no recorded basis**
The documented mint pointer is **AC-294** (`sequence/USER_STORIES.md:1101`) and the highest existing story is **US-87**. Minting from AC-302/US-90 implicitly reserves AC-294–301 and US-88–89 for MRQ-207 — but MRQ-207 sits in backlog with no plan, and no allocation is recorded in its task description, `org-settings-design.md` (which explicitly says "minted at consolidation, never here"), or run-state. If MRQ-207's planner follows the documented Next-mint line, both tickets claim overlapping IDs; if MRQ-207 needs anything other than exactly 8 ACs and 2 USes, the numbering fractures. The plan's mitigation ("expected rebase conflict … resolves to the higher value") repairs only the *Next mint:* line — it cannot repair overlapping AC IDs already baked into test claims and `trace:ac` manifests, and renumbering stable IDs post-mint is the failure stable IDs exist to prevent.
**Recommendation:** Either mint from the documented pointer (AC-294–AC-299, US-88–US-89) and let MRQ-207 mint above at its own consolidation, or have the captain/intake session record the range split in run-state or both tickets *before* the contract commit. Minting is effectively single-writer in this project for good reason; an undocumented gap assumption imports the same hazard.

**[MAJOR] Step 2 (Shared deletion seam) — the unification's divergence points are named but not decided**
`remove-demo` and delete-conference genuinely differ in at least four behaviors: audit rows (deleted vs. preserved — the critical issue above), `people` (demo people deleted vs. all people preserved), person-anchored rows (`magic_links`/`auth_sessions`/`api_tokens`/`memberships` deleted via the person predicate vs. untouched), and the `demo_mode`-flip side effect. The plan gestures at the right outcome ("preserve organization rows and audit history … keep demo removal idempotent and scoped") but never states the seam's parameterization — what varies per caller and what the one primitive owns. Left implicit, this gets litigated in code review, or worse, `remove-demo`'s AC-286 behavior silently changes under the refactor.
**Recommendation:** In the SPEC amendment (step 1), state the unified primitive's contract explicitly: shared core = event-scoped cascade in child-first order; per-caller policy = event selection predicate, people handling, audit handling, post-delete side effects. Add an AC-286 non-regression assertion to step 5 so unification provably preserves remove-demo's existing semantics.

**[MINOR] Step 5 (Regression coverage) — cascade completeness is a static list racing concurrent schema growth**
MRQ-208 (attendee schedules) is building on a parallel track and introduces new event-scoped state (`event_attendances`, schedule codes). A hand-enumerated cascade — like `REMOVE_DEMO_STATEMENTS` today — silently misses tables added after it was written; the before/after snapshot test only proves the tables it knows about.
**Recommendation:** Make the completeness test structural: enumerate every table carrying an `event_id` column (via `PRAGMA table_info` / `sqlite_master`) and assert each is covered by the deletion primitive (or on an explicit survivor allowlist — `attachments`, `audit_log`). This future-proofs both delete-conference and remove-demo in one test and turns "new event-scoped table" into a loud failure instead of a leak.

**[MINOR] Step 4 (UI) — prototype dies-list copy is narrower than the contracted cascade**
The v1.15 modal's "Dies with the conference" line reads "Abstracts and sessions · forms and their public links · agenda and conference site · speaker portal access · queued calendar invites" — it omits queued outbox mail and event embeds, both of which the contract cascade kills. The plan commits to reproducing the prototype copy *and* to a dies/stays-disclosure AC; as written those two commitments diverge.
**Recommendation:** Decide at contract time (step 1) whether the disclosure copy is amended to name outbox mail and embeds or deliberately stays at the prototype's altitude, and pin the exact strings in the AC so the UI test asserts one truth.

**[MINOR] Step 4 (UI) — "another conference" landing is nondeterministic as specified**
With two-plus surviving conferences, which one receives the post-delete navigation is unspecified (picker order? most recently active?). Untestable as written, and a coin-flip UX.
**Recommendation:** Pin the rule in the AC (e.g., the picker's first/most-recent conference) so the landing-branch test in step 5 asserts a specific destination.

### 4. Positive Observations

- **The rebase-conflict anticipation is genuinely good planning.** Naming the `Next mint:` line as an *expected* conflict with a resolution rule, and deferring rebase to the captain's order after MRQ-203, shows the planner understands this fleet's concurrency model — even though the AC-range half of the problem still needs the fix above.
- **The wart is respected.** Explicitly carrying "leave `attachments.event_id` semantics unchanged" into the seam step honors a standing project rule that would be easy to trample in a deletion refactor.
- **Both confirm-gate arms are tested.** "Test mismatch and exact match," with the `value.trim() === event.name` predicate stated, mirrors the prototype's tested-both-ways ruling rather than just the happy path.
- **Agent-native parity is one operation, not two.** "CLI verb that calls the same route … without creating a second operation" is exactly the right reading of the parity requirement and of this codebase's route-registry discipline.
- **The byte-identical survivor assertion is the right strength.** Counting is weak; "people/notes/tags byte-identical before and after" is the assertion that would actually catch a predicate that nibbles org-scoped rows.
- **Validation goes to the real running artifact** — Worker/API proof and the real UI flow, not just green units — consistent with the project's smoke-launch discipline.
