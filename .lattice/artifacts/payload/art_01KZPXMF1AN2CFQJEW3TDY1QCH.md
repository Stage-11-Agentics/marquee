# Plan Review: MRQ-4 — Seed generator (spine)

## 1. Verdict

**FAIL (plan-level)**

## 2. Summary

The plan's data modeling is careful and well-grounded — it was checked against the actual source JSON (60 TALK/WORKSHOP sessions, 75 unique speakers, 3 of the 60 without named speakers), the current schema (`migrations/0001_init.sql`, `src/db/schema.ts`), and SPEC.md's later, binding Amendment 11 text rather than the ticket's stale "four buildings" wording. The blocker is process, not content: the plan edits `package.json` (a new `seed` script plus an `engines.node` bump) even though BUILDPLAN §7 names `package.json` as an M-06-owned shared file where "dependency additions are the only other edits, and they queue" through the orchestrator — this ticket's own "Shared files" line only authorizes `scripts/seed/index.ts`. The `engines.node` bump also has no effect on the one place Node version is actually pinned (`.github/workflows/ci.yml`, hardcoded to `20.19.0`), so the plan's own architecture (`node scripts/seed/index.ts` relying on native TS execution) is left unreconciled with CI. A second, independent issue — the `forms.kind='session'` workaround for the Hotel/Travel task-form — resolves a real schema gap in a way that leaks into another ticket's user-facing surface (the public Forms catalog) without an architect ruling.

## 3. Issues

**[CRITICAL] `package.json` edit — violates the shared-file serialization contract**
BUILDPLAN §7's shared-file table is explicit: `package.json (scripts) | M-06 | The full thirteen-command script table registered at once... Dependency additions are the only other edits, and they queue.` MRQ-4's own "Shared files" line names only `scripts/seed/index.ts` as the file it owns. The plan's Deviation #2 nonetheless adds `"seed": "node scripts/seed/index.ts"` and bumps `engines.node` from `>=20.19.0` to `>=22.18.0` directly in `package.json`, describing this as "Flagged to the Orchestrator" — i.e., disclosed in the completion report, after the edit lands, not serialized/approved beforehand. That is exactly the failure mode §7 exists to prevent ("Sixteen tickets writing into one repo overnight fail on shared files, not on logic"). With M-01/M-03/M-05a/M-05b/M-06/M-07 all landing in the same Wave 0 window, an unserialized edit to an M-06-owned file is a concrete overnight merge-conflict / silent-clobber risk, not a hypothetical one.
**Recommendation:** Before implementation, either (a) get the orchestrator to serialize this specific `package.json` edit ahead of time (the model §7 already prescribes for `wrangler.jsonc` additions), or (b) drop the `package.json` edit from this ticket's scope entirely and have M-03 (which is the ticket that actually calls `reset:demo` → seed, per BUILDPLAN's M-03 row) or the orchestrator register the `seed` script as part of a coordinated pass. Do not let a 2h fast-track ticket edit an M-06-owned file on its own authority.

**[MAJOR] `engines.node` bump doesn't reconcile with CI's actual pinned Node version**
`.github/workflows/ci.yml` hardcodes `node-version: 20.19.0` in `actions/setup-node` — it does not read `engines` from `package.json`. The plan's chosen seed architecture runs `node scripts/seed/index.ts` directly, relying on Node's native TypeScript execution, which requires roughly Node ≥22.6 (the plan itself invokes this reasoning to justify the bump: "native type-stripping; `schema-verify.mjs` already requires ≥22.5"). Bumping `engines.node` does nothing to change what Node version any CI job actually runs on. `.github/workflows/ci.yml` is also M-06-owned and untouched by this plan, so the inconsistency is left dangling: any current or future gate job that runs `npm run seed` on the pinned 20.19.0 runner will hard-fail parsing the `.ts` entrypoint, and there is no mechanism in this plan to prevent or catch that.
**Recommendation:** Either flag this explicitly as a cross-ticket follow-up (ci.yml's Node pin needs to move in lockstep with any `engines.node` bump, and that edit also needs to serialize through M-06's owner) or avoid raising `engines.node` at all — e.g. ship the seed as `.mjs` matching the rest of `scripts/checks/*`, consistent with what's actually exercised by CI today, and take the type-stripping dependency out of the critical path entirely.

**[MAJOR] `forms.kind='session'` workaround leaks into another ticket's surface without a ruling**
`forms.kind` is `CHECK (kind IN ('abstract', 'session'))` — both values are CFP-submission-form kinds (SPEC §5.4: the `/forms` catalog, "each card shows name, kind, status..."; SPEC line 186: `submissions.kind` is inherited from `forms.kind` and feeds "type chip in every list (AC-23), evaluation eligibility"). `task_templates` requires `form_id NOT NULL` when `kind='form'` (`CHECK (kind <> 'form' OR form_id IS NOT NULL)`), so seeding the Amendment-4 "Hotel and Travel Reservations" task-form forces a real `forms` row to exist. The plan's chosen value, `kind='session'`, is correctly self-identified as "least-wrong," but it means a non-CFP, admin-internal task form will appear in the public `/forms` catalog tagged as a session-type CFP form, and will be visible to any downstream logic that trusts `forms.kind`/`submissions.kind` for type chips or evaluation eligibility (M-08, M-09, evaluation tickets — none of which are party to this decision). This is a real schema gap (Amendment 4 was folded in after the schema had no room for a "task-intake form" kind), and it affects more than this ticket's own file surface.
**Recommendation:** Escalate to the orchestrator/architect for a ruling before implementation rather than resolving unilaterally — e.g. a schema amendment adding a third `forms.kind` value, or keeping `task_templates.form_id` pointed at a form that is explicitly excluded from the public catalog by some other flag. If time genuinely doesn't allow a schema change before this ticket's window, at minimum add an assertion the delegator can point downstream tickets at (e.g. a code comment plus a lattice note to M-08/M-09 authors) so the leak is discoverable before it's discovered as a demo-visible bug.

**[MINOR] Extra "Online" room not in SPEC §6, added to a file this ticket owns outright**
SPEC §6 lists exactly 9 rooms (3 ballrooms + Expo Stage + Workshop Rooms A–E) for the 3-building trio; the Online building is listed with zero rooms. The plan adds a 10th room, "Online" (capacity 0), reasoning that otherwise the 2 real Online-format accepted sessions could never be scheduled by M-04b. That's a reasonable forward-looking call, but M-04b's own plan doesn't exist yet, and `event.ts`/rooms is entirely within M-04a's exclusive file surface — if M-04b's (not-yet-written) plan makes different room-count assumptions from SPEC §6's literal list, this ticket's addition could silently conflict with it.
**Recommendation:** Keep the addition (the reasoning is sound), but make sure it's surfaced somewhere M-04b's delegator/reviewer will actually see it before that ticket is planned — not just buried in this ticket's "flagged in completion" note, which by definition lands after M-04a already merged.

**[MINOR] Synthetic "Program Committee" submitter isn't listed among the flagged deviations**
`submissions.submitter_person_id` is `NOT NULL`, and the source data confirms 3 of the 60 accepted TALK/WORKSHOP sessions carry no named speaker (`content_sessions_with_named_speakers: 57` vs. `content_sessions_talk_or_workshop: 60` in `sources/aie-summit-2025-program.json`), so a synthetic submitter-of-record is a genuine necessity, not a shortcut. But it's the same category of decision as the five items the plan does flag (inventing something not in the source data to satisfy the schema) and it isn't in that list — it's mentioned only in passing inside the `event.ts` architecture bullet.
**Recommendation:** Add it as a sixth flagged deviation so reviewers checking "no invented identities" concerns (privacy/no-real-emails rules, speaker-directory rendering) see it with the same visibility as the others.

**[MINOR] Ticket's "Human precondition" (Airtable demo base) isn't addressed**
The ticket text carries an explicit precondition: "Airtable demo base on Team or above before this seed runs" (trap 6). The plan's chosen mechanism writes directly to D1 via generated SQL with "no outbound HTTP anywhere" — meaning, on the face of it, this ticket's own seed run has no Airtable dependency at all (mirroring is a separate write path per BUILDPLAN's Airtable ruling). The plan never says this, so a reader can't tell whether the precondition was considered and found inapplicable, or simply missed.
**Recommendation:** Add one sentence noting whether/why the Airtable precondition does or doesn't gate this specific ticket's execution.

## 4. Positive Observations

- The five flagged deviations are unusually well-substantiated: each is checked against the actual current state of SPEC.md/DESIGN.md/the schema rather than the (sometimes stale) ticket text, and each includes the concrete evidence for the discrepancy (e.g., correctly identifying that SPEC's Amendment 11 text already supersedes the ticket's literal "four buildings," and that `skin-c.html` defines only 7 of DESIGN.md's stated 8 track colors).
- Numbers check out against the real source data: 60 accepted TALK/WORKSHOP sessions, 75 unique speakers, and 32/28 wave split all match `sources/aie-summit-2025-program.json` exactly.
- Idempotency design (deterministic slug IDs, upsert-only, never-delete) correctly protects M-04b's later pool data from being clobbered by a spine re-run, and is exactly what lets `reset:demo` (M-03) call this seed safely.
- `scripts/seed/index.ts` is kept to pure glob-and-orchestrate, matching BUILDPLAN §7's rule for that specific file precisely, and the out-of-scope list cleanly matches M-04b's actual BUILDPLAN row (pool, evaluations, agenda, ugliness) — no scope creep into that ticket's territory.
- The validation plan (direct SQL assertions against a real local D1 plus a double-run idempotency check) is proportionate given that `check:seed`/`check:api` are still stubs this ticket can't yet lean on.
