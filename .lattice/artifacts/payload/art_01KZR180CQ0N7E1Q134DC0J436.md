### 3. Issues

**[MINOR] src/routes/public-form-routing.ts:135–183 — Plan-only target with zero rounds is not refused**
Resolution 4 says "Missing/closed/no-round targets fail with the same public-safe 422" and that a plan target's "lowest-position round is selected." `resolveTarget` validates a plan-only target as open but only resolves a round when a committee is present (line 166); a plan-only target pointing at an open plan with no rounds silently succeeds and stamps the rule. Practical impact is nil today — nothing is written for plan-only routes beyond the `applied_rule_id` stamp — but it deviates from the letter of the resolution.
**Fix:** For a plan-only target, verify the plan has at least one round (reuse the existing round-selection query without the committee condition) and throw `routingFailure()` when it doesn't — or record the accepted narrowing in the ticket's review artifact.

**[MINOR] src/routes/public-form.routes.ts:609 — Redundant `persistTracks` for committee-routed submissions**
When `routingStage` is non-null, tracks were already persisted during staging (`public-form.routes.ts:306` via `stageRoutingSubmission`); line 609 deletes and re-inserts the same rows with fresh UUIDs. Harmless because `persistTracks` is idempotent, but it's two extra write statements on the public submit hot path — and speed is a graded feature (R7).
**Fix:** `if (routingStage === null) await persistTracks(...)`.

**[MINOR] src/routes/public-form.routes.ts:571–612 — No cleanup if a write fails between guard pass and final UPDATE**
The rollback (line 580) covers only guard refusal. If a D1 write throws after `assertRoutingPoolAllowed` passes but before the status UPDATE completes, a routed new submission leaves an orphaned draft shell, staged tracks, and possibly a created person. This matches the codebase's existing non-transactional norms (the pre-existing INSERT-then-write sequence has the same exposure), so it is not a regression — noted for completeness.
**Fix (optional):** Widen the `try` to cover the writes through the status UPDATE and reuse `rollbackRoutingStage` in the catch, rethrowing the original error.

**[MINOR] src/routes/public-form-routing.ts:102–110 — `scalarEqual`'s `String()` fallback is looser than intended**
The final fallback `String(actual) === String(expected)` lets `value: 1` match `"1"` and makes any two non-array objects compare as `"[object Object]"`. Defensive leniency for hand-authored rule JSON is reasonable, but the object case is an accidental match vector.
**Fix:** Restrict the coercion fallback to `typeof` string/number/boolean operands and return false otherwise.
