# Plan Review — MRQ-13 (BUILDPLAN M-12: form builder, catalog, condition evaluator)

## 1. Verdict

**FAIL (plan-level)**

The revision needed is additive, not a rewrite: two owned Tier-A criteria have no step in the plan at all, and one asserted rule has no backing column while the plan simultaneously forbids a migration. Everything else below is tightening.

## 2. Summary

Reviewed the MRQ-13 plan against the ticket description, `BUILDPLAN.md` (M-12, §7), `EVALUATION.md` (AC-17–AC-21, AC-24, AC-27–AC-33, AC-132/133, AC-234), `SPEC.md` §5.4/§5.5, the live schema in `migrations/0001_init.sql`, the seed in `scripts/seed/`, and the check harness (`scripts/checks/trace-ac-core.mjs`, `pr-gate.mjs`). The plan is well above average — the shared-evaluator seam is exactly right, the seven builder steps match the binding prototype verbatim, and the boundary section correctly refuses to touch the frozen artifacts and the generated route manifest.

The key concern is proof coverage for the owned AC set. **AC-33 (four outbox assertions) is not mentioned anywhere in the plan**, and **AC-21's "has ever opened" predicate has no column in `forms`** while the plan rules out a migration. Both are Tier A, no-waiver, and owned by this ticket for `trace:ac`.

## 3. Issues

**[CRITICAL] Verification artifacts / API and query layer — AC-33 is entirely unaddressed**
The plan owns AC-33, which `EVALUATION.md:208` verifies as *four* outbox assertions: draft resume link, pre-close reminder (scheduled handler invoked), thank-you on submit, and named-admin new-submission notice. The plan mentions "message/admin settings" and a Messages step, but never the outbox, `enqueueTrigger`, or a test. The infrastructure is half-built and half-absent, which is why this needs deciding at plan time, not discovery time: `src/jobs/mail/triggers.ts:67` already ships `enqueuePreCloseReminders` (wired to the hourly cron at `src/index.ts:151-156`), so assertion 2 is a wiring test over `forms.reminder_offset_hours`. But `enqueueTrigger` has **exactly one caller in the repo** (`triggers.ts:87`) — there is no submit path, no draft path, and no admin-notice emitter anywhere, and `forms.thankyou_template_key` / `forms.admin_notify_person_ids` (`migrations/0001_init.sql:230-233`) are currently write-only columns nobody reads.
**Recommendation:** Add an explicit AC-33 section stating, per assertion, where the emitter lives and what proves it. The seam-preserving shape: MRQ-13 exports the trigger-emitting primitives (thank-you, admin notice, draft resume) from `forms.queries.ts` keyed off the form's message settings, tests them directly against the outbox table, and MRQ-15's public writer *calls* them — the same "built here, consumed there" contract the plan already applies to `isFieldApplicable()`. If instead the emitters are deferred to MRQ-15, say so and move AC-33 to that ticket's `owns` in the claims file rather than claiming it here.

**[CRITICAL] API and query layer — "has ever opened" has no backing column, and the plan forbids the migration that would add one**
The plan states: *"A form whose status is `open` or has ever opened cannot change `kind`"* and, three paragraphs earlier, *"No migration rewrite or replacement schema is planned."* The `forms` table (`migrations/0001_init.sql:216-243`) has `status`, `opens_at`, `closes_at` — **no `opened_at`/`first_opened_at`**. A draft→open→closed form and a form set straight to `closed` are indistinguishable by `status` alone, and `opens_at` is a *scheduled* date that may be set on a form that never opened. AC-21 (`EVALUATION.md:181`) asserts the immutable-after-open rule, so an implementer hitting this mid-build will either invent a derivation silently or add an unplanned migration.
**Recommendation:** Decide now and write it down. Either (a) define the predicate as derived — e.g. `status = 'open' OR status = 'closed' OR (opens_at IS NOT NULL AND opens_at <= now)` — and state the accepted false-positive (a scheduled-but-never-opened form locks its kind), or (b) add `migrations/0003_mrq13_forms_opened_at.sql` as an additive `ALTER TABLE`, which is the established precedent (`migrations/0002_venue_geography.sql:1-3` does exactly this and names its ticket). Option (b) is cleaner and costs ~10 minutes; either way the plan's "no migration" line needs amending.

**[MAJOR] Verification artifacts — no stated proof strategy for the five ACs whose verification is `e2e:` over the public form**
Of the 16 owned criteria, five are verified against a surface this ticket does not build: AC-17 (*"assert public form field order matches the builder"*), AC-18 (*"e2e: renders and submits one of each on the public form"*), AC-19 (*"extract … from the builder preview and from the public URL; assert deep-equal"*), AC-29 (*"limits stated before the first add-person control"* — SPEC §5.5 places this sentence on `/f/:slug`), AC-30 (*"welcome copy … rendered before the first field"*). The public form is MRQ-15 / M-14, file surface `src/routes/public-form.route.tsx`. The plan gestures at this once ("the same `{label,type,position,required}` source used by the future public form") but never states the split. Left unstated, the implementer either builds a public-form slice inside MRQ-13 (scope creep across a §7 file boundary) or ships a claims file whose green is structurally uninformative.
**Recommendation:** Add a short table to the verification section: AC → what MRQ-13 proves now (unit/integration over the shared projection and query layer) → what MRQ-15 completes (the e2e half). The ticket description already establishes this pattern for AC-132/133; apply it explicitly to AC-17/18/19/29/30 and note the deferred halves in the PR description so the M-14 delegator inherits them.

**[MAJOR] Verification artifacts — `trace:ac` requires a titled test for *every* owned auto criterion, not just AC-132/133**
The plan commits only to *"at minimum, one test title explicitly includes `AC-132` and one explicitly includes `AC-133`."* The harness is stricter than that in two ways. First, `buildCoverage` (`scripts/checks/trace-ac-core.mjs:83-88`) enforces every id in `owns` that is tagged `auto` — all 16 here are — and reports it in `uncovered` if no test title carries it, failing the gate. Second, the title grammar is exact: `scanTestSource` (`trace-ac-core.mjs:41`) requires the prefix `AC-\d+(, AC-\d+)* · ` — an ASCII-hyphen id list followed by a **middot** separator — and rejects anything else as `invalid-title-prefix`, including the plan's own prose form "a test title that includes AC-132".
**Recommendation:** Replace the "at minimum" sentence with the full 16-row AC → test-title map, written in the literal `AC-17 · …` form. Also fix the invocation: `parseArguments` accepts `--scope` only as `merged` or `all` (`scripts/checks/trace-ac.mjs:19` throws otherwise), so the plan's `--scope=...` placeholder should read `npm run trace:ac -- --ticket MRQ-13`.

**[MAJOR] Verification artifacts — ownership collision with the public-form ticket is unflagged, and `duplicate-owner` is a hard error**
The plan claims `owns: AC-27–AC-33`. BUILDPLAN's M-14 row (`BUILDPLAN.md:74`) lists `AC-25, AC-26, AC-29, AC-30 – AC-42` — an overlap of AC-29 through AC-33. `trace-ac-core.mjs:77` emits `duplicate-owner` and fails the gate the moment two claim files list the same id. Claiming them here is defensible (MRQ-13 lands first, and the ticket note sets the precedent for AC-132/133), but silence guarantees the collision surfaces as a red gate on someone else's PR.
**Recommendation:** State in the plan that MRQ-13 owns AC-29–AC-33 and that MRQ-15 must list them under `exercises`, not `owns` — and file that instruction as a note on the MRQ-15 ticket at PR time, not just in this plan.

**[MAJOR] API and query layer — the AC-31/AC-32 enforcement seam is unnamed, inviting the exact duplication the evaluator seam exists to prevent**
AC-31 (closed form: GET 200 with closed copy, POST 4xx, zero rows) and AC-32 (per-form submitter limit enforced at 1, 3, and 5) are both verified on public write paths. A repo grep shows **no reader of `per_submitter_limit` anywhere in `src/`** and no close-state gate — these primitives do not exist yet. The plan gives `isFieldApplicable()` and the answer projection a durable home and an explicit "must not be duplicated in MRQ-15" rule, but says nothing equivalent for the closed-state and limit gates; it only notes that closed writes are "rejected before any row is written."
**Recommendation:** Name the export (e.g. a `formIntakeGate(form, submitterContext)` in `forms.queries.ts`, or extend `src/lib/form-conditions.ts` if it must be browser-safe) that returns the closed / at-limit / open verdict plus the SPEC §5.5 copy key, prove it in unit tests here, and record it in the plan's shared-contract list so MRQ-15 consumes rather than re-derives it.

**[MAJOR] Seed and form domain data — the seed file surface is unnamed, and the field the plan is about to renumber is another ticket's Drafts-queue fixture**
The plan says "extend the existing deterministic seed" without naming a file. Concretely: the CFP form's *only* seeded field today is `audience_outcome` at **position 0**, seeded in `scripts/seed/pool.ts:239-255` (M-04b's file), with a comment declaring it exists so *"the built-in Drafts queue [has] something currently applicable to report as missing"* — i.e. it is M-55's fixture. The hotel/travel form's fields are in `scripts/seed/event.ts:250-272` (M-04a's). The plan's "builder order" registry puts title/abstract first, which renumbers position 0. Meanwhile `scripts/seed/index.ts:51-60` discovers seeders by directory glob and is M-04a-owned "orchestration only" under §7.
**Recommendation:** State the file decision: add `scripts/seed/cfp-form.ts` as a new glob-discovered seeder (preferred — no §7-owned file is edited), move or re-position `audience_outcome` there deliberately, keep its deterministic id `seedId("fld","cfp-audience-outcome")` and its `required: 1` + `minLength: 20` config intact so the Drafts-queue semantics survive, and confirm `scripts/seed/index.ts` is not edited.

**[MINOR] Flight Deck UI — the Rules & routing boundary against M-37 is not drawn**
SPEC §5.4 puts "routing rules" in the Rules & routing step; M-37 (`BUILDPLAN.md:121`, AC-135–137) owns category routing. The plan lists the step and says duplicate copies "routing configuration," implying `routing_rules` rows, but never says whether rule CRUD ships here. Both failure modes are live: an implementer builds routing (scope creep, +hours on the longest ticket) or ships a visibly dead step in walkthrough step 4.
**Recommendation:** State it in one line — e.g. per-field validation and conditional logic ship here; routing-rule rows are read/copied but authored by M-37, and the step renders an honest, non-dead placeholder until then.

**[MINOR] Contract and boundaries — the M-09 dependency is still in flight, and AppShell is contended**
`Deps: M-09`, but the Event settings ticket is `in_progress`, not merged (Lattice status), alongside M-17, M-18, and M-19a. The plan pins the baseline commit and the passing suite but never mentions the dependency's state. Two contact points: the CFP registry's format and multi-track fields read M-09's formats/tracks, and `src/ui/shell/AppShell.tsx:44-51` is the single mount switch every in-flight UI ticket must edit.
**Recommendation:** Add a line naming what MRQ-13 assumes from M-09 (the seeded formats/tracks it reads, already present in the seed) and confirm it does not block; and note that the AppShell mount is a two-line addition to be rebased last, kept minimal to reduce conflict surface. `src/ui/shell/route-table.ts:24` already carries the `/forms` entry — the plan is right that it should not be edited.

**[MINOR] Flight Deck UI — three SPEC §5.4 states and one prototype detail are absent**
SPEC §5.4's States line requires an **unpublished-changes badge** and the open / closed / at-limit / resumed-draft **preview** states; §5.4 also specifies the live preview sits *"in a browser-chrome frame that matches the public form exactly."* The plan covers the immutable-target explanation (good — it correctly reads "not a disabled control with no reason") but not these.
**Recommendation:** Name the unpublished-changes badge and the preview state switcher in the UI section, and specify the browser-chrome frame. `pr-gate` runs `check:design` (`scripts/checks/pr-gate.mjs:16`), so prototype fidelity is a gate, not a nicety.

**[MINOR] Flight Deck UI — one component file for a catalog plus a seven-step builder, and no builder URL**
The plan names exactly `src/ui/forms/FormsPage.tsx` and `forms.css`. The catalog, a seven-step rail, full field CRUD with reorder, and a live preview in one file will land well past any reasonable module size, and the plan never says whether the builder gets its own route (`route-table.ts` has only `/forms`, and per-form deep links are what the walkthrough and later e2e need).
**Recommendation:** Sketch the decomposition under `src/ui/forms/*` (catalog, builder shell, per-step panels, preview) — the §7 file surface already permits it — and decide whether `/forms/:id` joins the route table as a `utility` entry.

**[MINOR] Whole plan — no build ordering for the longest ticket on the critical path**
M-12 is 10 h and sits on the CP-2 critical path (`BUILDPLAN.md:241`: M-09 → M-12 → M-14 = 22 h, one hour of margin). The plan is written as one undifferentiated pass, so a time overrun lands wherever the implementer happened to stop.
**Recommendation:** State the order explicitly — `form-conditions.ts` + its tests, then the API/query layer, then the seed, then the UI — so that if the ticket runs long, what exists is the seam MRQ-15 and MRQ-56 are blocked on rather than a half-built builder screen.

## 4. Positive Observations

- **The shared-contract section is the best part of the plan and gets the hard call right.** Fixing the persisted shape as `{ all: [{fieldKey, op, value}] } | null`, making `isFieldApplicable()` the single applicability decision point, failing closed on malformed operators, and — crucially — exporting the *server-side answer projection* as the AC-133 proof boundary with an explicit "must not be duplicated in MRQ-15" is precisely the reasoning that justified moving the evaluator out of M-36. Keeping it dependency-light and browser-safe so the builder preview, the SSR public form, and M-55's applicable-missing-fields query share one implementation is the right constraint, stated at the right time.
- **The seven builder steps match the binding prototype verbatim.** Type & basics · Welcome · Form fields · Participants · Rules & routing · Messages · Publish all appear in `prototypes/pipeline-v1.1/index.html`. The plan was written with the prototype open, not from memory.
- **The boundaries section refuses the right things**: no edits to the frozen contract artifacts, no hand-edited route manifest, no second pagination shape, no invented auth path, no replacement schema. Naming the baseline commit and the passing baseline suite (21 files / 110 tests) makes the later diff auditable.
- **Fail-closed authorization is stated up front**, with reviewers and speakers excluded from every authoring path — not left to be discovered at review.
- **Real craft rules are carried into the UI section**: fixed-width segmented controls, `—` placeholders, preview that does not reflow the editor, text-not-colour state labels, keyboard-safe reorder alongside drag, and the ruling that the immutable post-open target is explained rather than silently disabled. That last one is a direct read of SPEC §5.4's States line and is easy to miss.
- **The delete/reorder invariant is stated as an invariant** ("never let delete/reorder leave gaps or duplicate positions") rather than as a feature — the correct altitude for a rule that a later ticket can violate by accident.
