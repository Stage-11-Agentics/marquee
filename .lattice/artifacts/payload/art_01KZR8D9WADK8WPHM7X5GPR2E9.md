## 3. Issues

**[MAJOR] scripts/seed/submission-content.ts:59-66 (+ src/ui/review/ReviewerPage.tsx:423, src/routes/review.routes.ts:311-327) — Acceptance 2 unmet: 4 of 8 reviewer-detail rows still read "Not answered"**
The detail's fields subquery returns every non-identity `frm_cfp` field: `title`, `abstract`, `audience_outcome`, `format`, `tracks`, `supporting_file`, `vendor_content`, `vendor_product` (8 rows). The seed answers only `audience_outcome`, `format`, `tracks`, `vendor_content` (+`vendor_product` on the 1-in-11 vendor subset), and `ReviewerPage.tsx:423` renders the full list through `displayField`, whose fallback at `:143` is the literal "Not answered". Confirmed at runtime: the check's own evidence records `populated_fields: 4` of 8 on the first queue card. A judge sees "Session title — Not answered" and "Abstract — Not answered" directly beneath a header that displays the real title and a "Full abstract" section that displays the real abstract — which reads as *broken*, not merely sparse — plus "Not answered" for `supporting_file` even when the card's file section shows an attachment, and for the inapplicable `vendor_product` (the display-side twin of the AC-133 "absent, not null" rule this same ticket enforces on the write path). The acceptance text is explicit: "no row reading 'Not answered'".
**Fix:** Two contained halves. (a) Seed the trivially-mirrorable answers: `title` and `abstract` answer rows copied from the submission columns (deterministic, no new content). (b) For the remaining two, fix the rendering rather than fake data: skip inapplicable conditional fields using the shared `isFieldApplicable` (already exported; using it here is exactly SPEC's one-evaluator rule), and render unanswered optional `file`-type fields as a pointer to the attached-files section (or omit them) instead of "Not answered". Then raise `scripts/checks/seed.ts` from `populated_fields >= 4` to asserting **zero** rendered-and-unanswered rows, so the gate proves the acceptance rather than the current state.

**[MINOR] tests — the plan's promised statement-count probe was not shipped (acceptance 5, first half)**
The plan committed to "a speed/shape probe that proves the queue performs single-digit D1 statements". What shipped is a structural contract update (`tests/node/reviewer-boundary.AC-214-246.test.mjs` now asserts `reviewerQueue` calls `authorizeReviewerQueueScope`), which prevents the deleted duplicate-authorize from returning in that exact shape but counts nothing. I verified the property statically — a ≤80-card queue load is exactly 5 statements (`roundForEvent`, `assignedSubmissionIds`, one batch authorize, one `queueRows` chunk, `reviewerTrackScopes`) — but nothing mechanical fails if someone reintroduces a per-card loop inside a helper the contract test doesn't inspect.
**Fix:** In `tests/integration/api/reviewer-queue.AC-59-65-244-246.test.ts`, wrap `env.DB.prepare` in a counting spy around one queue GET and assert the count ≤ 9. Ten lines, and acceptance 5 becomes regression-proof.

**[MINOR] src/lib/reviewer-scope.ts:190-193 — `roundEventId` guard is vacuous at every call site**
All three callers pass `roundEventId: eventId`, so `request.roundEventId !== request.eventId` can never be true; the real cross-event protection is that `roundForEvent`/`activeRoundForEvent` join `plan.event_id = ?` before any call. The dead parameter implies a check that isn't happening and invites a future caller to trust it.
**Fix:** Drop the parameter (the round is always pre-validated on this path), or select `plan.event_id` into `RoundRow` and bind the round's actual event so the guard is real.

**[MINOR] scripts/seed/submission-content.ts:52-66 — byte-identical answer content across all 1,000 submissions**
Every card's `audience_outcome` is the same sentence, every vendor answer is "Northstar Observability", and every attachment is `supporting-material.pdf` at 4,096 bytes. Flipping between queue cards — the demo's core reviewer motion — shows identical prose under different titles, which reads as mock data on a graded screen (R7/walkthrough). Determinism doesn't require uniformity.
**Fix:** Pick from a small fixed pool keyed on submission index (e.g., 8–10 outcome sentences, a few filenames/sizes). Same byte-identical rebuild guarantee, visibly real data.
