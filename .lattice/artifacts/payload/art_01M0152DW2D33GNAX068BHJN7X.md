# Code Review: MRQ-208 — attendee schedule rounds 2+3 (PR #266)

Reviewed against the ticket contract, the plan, and the running code. I read the full diff, cross-checked the pre-existing infrastructure on `main` (grants model, import-undo path, outbox/consumer, turnstile, token minting), ran the branch's new integration suite in the `mrq-208` worktree (**17/17 pass, 11s**), ran `tsc --noEmit` (**clean**), and wrote a scratch reproduction for the one scenario I suspected — which **confirmed a live 500 with partial data deletion**. The scratch file was removed after; the worktree is clean.

## 1. Verdict

**FAIL (implementation-level)** — the plan and architecture are sound (and in several places better than the ticket asked for), but there are four implementation defects, one of them a confirmed 500 with data loss in a user-reachable flow. All are fixable inside the existing design; the task should return to `in_progress`.

## 2. Summary

This is a large, high-quality implementation: the demand signal, claim flow, CRM attendance model, and speaker pins all match the ruled semantics, with tests that assert the rulings rather than the code. The key finding is that **unlink breaks when the same email has verified claims on two schedule codes** (a person with a phone and a laptop): the endpoint 500s mid-deletion because the brand-new `schedule_claims.person_id` foreign key is missing from the person-reference inventory whose file promises to hold "every direct foreign key to `people`, in one place" — and before failing it deletes the attendance row the *other* still-verified claim legitimately backs. Three further defects: first-open verification silently no-ops on a fresh device (the core R2-2 recovery scenario), Resend is a dead end on Turnstile-gated events, and the advertised import undo cannot walk back an attendee import.

## 3. Issues

**[CRITICAL] src/lib/person-references.ts:822 — `schedule_claims` missing from the person-reference inventory; unlink 500s and partially deletes**
Reproduced live in the worktree: create two schedules, claim both with the same email, verify both (first claim mints the person, `minted_person=1`; second matches, `minted_person=0`). `DELETE /schedules/{codeA}/claim` then returns **500 internal_error**: the route deletes claim A's row and the shared attendance row, reaches the minted-person rule, `personReferences()` reports nothing (the attendance it would have caught was just deleted, and `schedule_claims` is not in the inventory), and `DELETE FROM people` hits the FK constraint from claim B's `person_id`. The FK is the only thing that prevented deleting a person another verified claim still points at. Because the deletions are sequential `.run()` calls, not a batch/transaction, the 500 leaves partial state: claim A gone, attendance gone, claim B still "verified" with no attendance row behind it.
**Fix:** (1) Add `schedule_claims` (`person_id`) to `PERSON_REFERENCE_CHECKS` — the file's own contract requires it, and this migration added the FK it misses. (2) In `unlinkClaim`, don't delete the claim-sourced attendance row unconditionally by `(person_id, event_id, source)`: delete it only if no *other* verified claim row for that person+event remains (or match `schedule_code = row.code` on the attendance). (3) Run the three deletions as a `batch()` so a failure can't strand half the outcome. Add the two-codes-one-email scenario as a test — it is exactly the "easy to regress" class the test file's preamble names.

**[MAJOR] src/ui/public/agenda/schedule-script.ts:1471–1479 (boot sequence) — first open of the mailed link on a fresh device never verifies**
`verifyClaimToken(claimToken)` guards on `state.code`, but on a device with no local state, `state.code` is only adopted inside `loadShared()`'s fetch *callback* — and the boot sequence calls `verifyClaimToken` synchronously right after `loadShared()` starts. So on the cross-device recovery path (claim requested on the laptop, mail opened on the phone — the very scenario R2-2 exists for), the verify silently no-ops, the token has already been stripped from the address bar, and the page shows "Saved on this device only" while the claim stays pending. Opening the mailed link a *second* time works, because the first open persisted `state.code` — the classic signature of this race. It will not show up when validating on the same browser that requested the claim, which is presumably why the walkthrough evidence looks green.
**Fix:** Verify with the code from the URL rather than local state — e.g. have `verifyClaimToken` use `sharedCode ?? state.code`, or chain it after `loadShared()`'s adoption resolves (`loadShared().then(() => verifyClaimToken(...)).then(loadOwnerState)`). Note the round-4 ruling is literally "first open of the emailed link = verification."

**[MAJOR] src/ui/public/agenda/schedule-script.ts:1195–1220 (renderClaimRow) + src/routes/public-claims.routes.ts:2277 — Resend is a dead end on Turnstile-gated events**
The server demands a Turnstile token on *every* claim POST unless the event is demo-exempt, and `verifyTurnstile` fails closed on a missing token (verified on main: `src/lib/r2/turnstile.ts`). The client only mounts the widget in the unclaimed input state; the pending and verified states render Resend/Cancel with no widget, `turnstileMounted` stays latched true, and Turnstile tokens are single-use — so the first Send consumes the only token and every Resend thereafter gets 403 "Complete the security check, then choose Send again" with no security check anywhere on screen. Currently masked twice over (demo events are exempt; the mail flag ships off), but Resend is a named deliverable and a dead end anywhere in the loop is a defect by project rule.
**Fix:** Include a Turnstile holder in the pending/verified renders and reset/re-render the widget after each send (`turnstile.reset`), clearing `turnstileToken` once consumed; or track the widget id and re-execute per send. Add the non-exempt path to validation once fixed.

**[MAJOR] src/routes/org-imports.routes.ts (importPeople + undo) — the advertised undo cannot walk back an attendee import**
Passing `event` writes attendance rows, but the undo route was not taught about them: every person *created* by an attendee import now carries an `event_attendances` reference, so undo skips them all with `has_references: ["event_attendances"]` (verified against the undo code on main — created-person deletion is gated on the same inventory), and nothing deletes the attendance rows themselves. Net effect: undo of an attendee import restores overwritten fields and nothing else — the people stay, and more importantly the conference's attendee population stays wrong. Meanwhile the agent brief this same PR ships tells the operator's agent to report "the import_id so I can undo it if it is wrong."
**Fix:** Make undo remove the import's own attendance rows before the reference check: record the resolved event id on the import receipt (or on `import_rows`), and in undo delete `event_attendances WHERE person_id = target AND event_id = ? AND source = 'import'` for each row, mirroring the ordering insight already written into `unlinkClaim` (attendances are themselves references, so they must go before the check). If receipt-schema work is out of scope for rework, the minimum honest change is to stop advertising undo in the attendee brief and document the limitation.

**[MINOR] src/lib/star-beacons.ts:1335 / src/lib/public-schedules.ts:896 — `DEVICE_HASH_PATTERN` defined twice**
Two identical regexes in two modules, both imported by routes. They will drift.
**Fix:** One definition; the other imports it.

**[MINOR] tests/integration/attendee-schedule-rounds23.MRQ-208.test.ts:4187 — the "never under the star" assertion tests CSS order, not DOM placement**
`on.indexOf("public-star-chip") > on.indexOf("public-format-chip")` compares *first* occurrences in the whole HTML document — and both class names appear first inside the embedded `<style>` block (`.public-format-chip` at style line ~105, `.public-star-chip` later), so the assertion passes on stylesheet source order and would keep passing if the chip moved under the star button.
**Fix:** Assert against the rendered card markup — e.g. slice the document from the first `public-agenda-row` before comparing, or assert the chip is inside `.public-meta-row` / not inside `.star-btn`'s parent.

**[MINOR] src/ui/public/agenda/PublicAgendaPage.tsx:3403 — detail-page inline count lacks the ruled copy and sr text**
The session page renders `★ N schedules`; the ticket's D3 asks for the copy "N schedules include this session" with sr text on the detail-page inline count as well as the chip (which has both).
**Fix:** Reuse `starCountLabel(count)` — as visible text or at least as the sr-only/`title` companion to the short form.

**[MINOR] src/lib/schedule-claims.ts:1019 — 1–2 character local parts are returned unmasked**
`maskEmail("ab@x.com")` returns the full address, which then flows to the pending/verified UI states. Tiny leak, but the masking contract is "the local part keeps only its ends."
**Fix:** Mask short locals too (e.g. `a…@x.com` / `…@x.com`).

**[MINOR] src/routes/public-claims.routes.ts (requestScheduleClaim) — demo events with the flag on will say "link sent" for suppressed mail**
`enqueueOutbox` takes the default `demo_safe` policy, and the consumer suppresses mail on demo events unless allowlisted — so once `ATTENDEE_CLAIM_MAIL=1`, a demo conference shows "Check your email — link sent to …" for a mail that will never arrive. Dormant today (flag off), and consistent with how other surfaces behave, but other surfaces use `demoMailWouldBeSuppressed` to tell the operator the truth.
**Fix:** Consult `demoMailWouldBeSuppressed` in the request route and answer honestly (or note the interaction in the flag's comment for whoever flips it).

## 4. Positive Observations

- **The rulings are enforced by tests, not just implemented.** "Sending writes no person," the exact unlink sentence, pins derived-never-stored, the shared link carrying neither claim nor pins while the ICS carries both, the beacon row's column set asserted so nothing identity-shaped can quietly join it — this is contract-grade coverage, and the test names say what regressed when they fail.
- **Security posture is consistently right:** write key required to attach/detach an email and never stored (used transiently to compose the sync URL, closing the open-mailer hole); claim tokens 192-bit, hashed at rest, compared constant-time; HTML escaped in the mail renderer; all client claim UI built with `textContent`; token and key stripped from the address bar on read.
- **The two-ceiling beacon limiter** (per-device shaping, venue-scale per-IP) is a genuinely better answer than the ticket's "schedules 30/hr/IP pattern" read literally — one NAT per conference is exactly the failure the naive copy would have shipped — and the deviation is documented where the numbers live.
- **`person-references.ts` extraction is the right refactor** — one inventory, two callers that must agree — which is precisely why the missing `schedule_claims` entry is worth fixing rather than patching around: the module's design makes the fix one line plus a test.
- The **event-settings homing** of the "org-level" setting is a well-argued, correctly-flagged deviation; `capacity = 0 → em-dash, never a fake ratio` and the `<1% of room` rounding honesty are exactly the taste rules the project claims to hold; the launch gate answers with an honest 409 instead of a silent queue; and the demand aggregate's two halves plus `COALESCE` on PUT keep the browser/agent de-dup semantics tight.
- Suite discipline held: schema-verify counts (56 tables, 111 FKs) updated and verified, `WIPE_ORDER` and reseed counts extended, migrations mirrored into the test harness, typecheck clean, and the new suite runs in ~11s.
