## 3. Issues

**[CRITICAL] src/ui/dashboard/DashboardPage.tsx:78–87, 111, 113 + src/routes/dashboard.routes.ts:157, 183–189, 219–221 — Onboarding destinations contradict the binding SPEC and prototype; the rejected plan decision shipped anyway**
SPEC.md §5.2 is explicit: "`Onboarding` → chase board; the rest → submissions list pre-filtered," and "speakers overdue (→ chase board)." The binding prototype routes the Onboarding stage, the overdue attention item, every task-preview row, and the "Open onboarding" button to the `onboarding` route (`src/ui/shell/route-table.ts:20` already maps it to `/onboarding`). The implementation instead invents a `status=onboarding` submissions filter and points all four surfaces at it — the exact architecture the plan review failed as CRITICAL ("don't invent the filter silently"), creating a second, competing definition of "Onboarding" that M-23 (chase board, Wave 2) will have to reconcile or discard. No SPEC amendment was obtained.
**Fix:** In the revised plan, either (a) route Onboarding surfaces to `/onboarding` per SPEC and record the AC-15 tension (an empty placeholder destination breaks the count-equals-results invariant) as an explicit interim gap with M-23 as the resolver, or (b) get a recorded SPEC/operator ruling authorizing the submissions-filter destination before rework. The derived predicate itself can stay — it's the destination that needs the ruling.

**[CRITICAL] tests/ac-claims/MRQ-11.json:3 + tests/integration/api/dashboard.AC-14-15-240.test.ts — claims ownership of three `e2e:`-contracted ACs (AC-240 Tier A, no-waiver) with integration-only evidence; `trace:ac` will report them covered**
EVALUATION.md rows 164, 165, and 579 contract AC-14, AC-15, and AC-240 to `e2e:` evidence; AC-240 is in the no-waiver Tier A set (§1.4 gate 18). `tests/e2e/` does not exist anywhere in the repo (`run-e2e.mjs` still stubs with `owner: "MRQ-50"`). Because `trace-ac-core.mjs:86-87` only checks that an `auto` AC has a matching `AC-N ·` test title — it cannot see the evidence tier — `npm run trace:ac` will report AC-14/15/240 green while the contracted evidence (a browser asserting rendered counts update with no reload, clicked tiles, and rendered stage copy) remains entirely absent. This is the identical silent-gap mechanism the MRQ-61 plan review just flagged for AC-105. Note also that the DOM renders the AC-240 copy as `{note} →` (DashboardPage.tsx:55) — the exact-copy assertion only ever runs against the API JSON, never the rendered surface the AC describes.
**Fix:** The plan must state the evidence position explicitly: either stand up `tests/e2e/` with the dashboard-liveness spec `validation-plan.md:33` names, or record an accepted deviation (integration-now, e2e-owed-by-MRQ-50/MRQ-9) in the plan, the PR, and the completion comment so the audit doesn't read `trace:ac` green as contract-met. Add a DOM-level assertion of the exact Scheduled/Published copy either way.

**[CRITICAL] tests/integration/api/dashboard.AC-14-15-240.test.ts:129 — the five-second-poll "assertion" is vacuous; DashboardPage has zero tests**
`expect(DASHBOARD_REVALIDATE_MS).toBe(5_000)` asserts a constant equals the value it was defined with. Nothing proves `DashboardPage` schedules a poll with it, clears the interval on exit, or aborts in-flight requests — the whole F-8 recorded decision, the honest state machine (loading/empty/error-with-stale-data/retry), and the abort/cleanup logic in `DashboardPage.tsx:132-160` are untested. The plan promised "assert the declared five-second revalidation interval without using a wall-clock wait" and the plan review demanded the mechanism be named before implementation; the implementation punted to a tautology.
**Fix:** Name and build the real mechanism: a component test (fake timers, or an injected scheduler seam the component reads) proving `setInterval` is registered with `DASHBOARD_REVALIDATE_MS`, a second fetch fires on tick, and cleanup clears the interval and aborts the in-flight request. If fake timers don't work under the Workers vitest pool, that constraint belongs in the plan with the chosen alternative.

**[MAJOR] src/ui/dashboard/DashboardPage.tsx:100, src/routes/dashboard.routes.ts:210–215 — Work-in-motion metrics silently swap two of the prototype's four instruments, including the Conflicts count MRQ-63 depends on**
The binding prototype's metric grid is Reviews done · Tasks overdue · Unscheduled · **Conflicts** (danger-colored, live). The implementation ships In review · Tasks overdue · Unscheduled · **Published** — "Reviews done" (an evaluations figure) became a duplicate of the pipeline's In-review count, and Conflicts vanished. This isn't only a DESIGN.md one-to-one violation: MRQ-63's contract ("must flow into the **existing dashboard count** … through the ONE existing getConflicts call") assumes the dashboard already renders a conflicts metric. Landing MRQ-11 without it silently breaks a dependency another dispatched ticket was written against.
**Fix:** Reinstate the four prototype metrics. If conflicts/evaluations data isn't available until the agenda/evaluation tickets land, render the instrument with an honest zero/pending state and record the acknowledged divergence — don't substitute a different metric.

**[MAJOR] src/routes/dashboard.routes.ts:183–189 + DashboardPage.tsx:86 — "N speaker tasks overdue" displays a count of submissions, not tasks**
`overdueSubmissions.count` is `COUNT(DISTINCT s.id)` — submissions carrying an overdue task — but the attention strip renders it as "`{count}` speaker tasks overdue". One submission with three overdue tasks reads "1 speaker tasks overdue." The prototype's figure counts speakers ("N speakers overdue") and its metric box counts tasks "across N speakers"; the implementation's copy matches neither its own number nor the prototype. For a project whose philosophy is honest instruments, a number that isn't what its sentence says is a defect, not polish.
**Fix:** Make copy and quantity agree — either count tasks and say tasks, or keep the submissions count and say "submissions with overdue speaker work." Align with whichever the prototype surface being reproduced actually shows.

**[MAJOR] src/ui/dashboard/DashboardPage.tsx:53–55, 101–102, 163 — further unacknowledged divergences from the one-to-one prototype reproduction**
DESIGN.md binds the build to the prototype; divergences must be explicit. Shipped silently: (1) the seven per-stage deltas — each a distinct derived figure ("+41 this week", "62% assigned", "N still unplaced", "N live conflicts") — replaced with static program-board hints ("Ready for review", "Committee work underway"…), and the Scheduled/Published AC-240 meaning-copy moved into the delta slot rather than the prototype's separate `.pipeline-meaning` span; (2) the page-head subtitle is static copy instead of the live wave/review-pressure sentence SPEC §5.2 specifies; (3) the next-wave attention item navigates to a submissions filter instead of scrolling to the wave planner (`data-scroll-wave`); (4) task-preview rows drop the `Not yet public` slot-meta pill (itself part of AC-240's surface contract); (5) the Work-in-motion Export button is gone; (6) a "Program mix by format" chip row was **added** with no prototype counterpart (AC-14 does require format counts somewhere — but the addition needs to be a marked, described divergence, not an unlabeled one).
**Fix:** Reproduce the enumerated elements, or list each divergence explicitly in the plan/PR with its justification, per DESIGN.md's acknowledgment rule.

**[MINOR] src/routes/submissions.queries.ts:63 — status literal interpolated into SQL instead of bound**
`return \`${submission}.status = '${status}'\`` inlines the value the previous code passed as a `?` binding. It is currently safe — `status` is the `SUBMISSION_STATUS_FILTERS` const union and the route validates via `z.enum(SUBMISSION_STATUS_FILTERS)` — but the function is exported, the safety is convention rather than mechanism, and the refactor quietly lowered the defense-in-depth bar for every future caller.
**Fix:** Have the predicate helpers return `{ sql, bindings }` (or accept a bindings array) so stored-status comparisons stay parameterized.

**[MINOR] src/routes/submissions.queries.ts:46–58 — "onboarding" counts any submission with an open speaker task, regardless of status**
The predicate is purely task-existence; a rejected or withdrawn submission with a lingering open task would count as Onboarding on the pipeline card. Today's invariant (tasks are only created on acceptance) makes this latent, and AC-15 consistency holds since both sides share the predicate — but the pipeline stage semantically means post-acceptance speaker work.
**Fix:** Add `AND {submission}.status = 'accepted'` to the onboarding predicate (or document the invariant where the predicate is defined).

**[MINOR] src/routes/dashboard.routes.ts:235–247 — unknown event returns a zeroed 200; overdue threshold drifts between dashboard and list**
There is no event-existence check, so a typo'd `eventId` (that clears the grant check) renders an all-zero dashboard indistinguishable from a real empty program — against the project's honest-empty-state stance. Separately, the dashboard evaluates "overdue" at snapshot `now` while the list evaluates it at its own `Date.now()` in `filterParts`, so an AC-15 comparison spanning a due-at boundary can mismatch by one (also a low-probability test flake in the AC-15 loop).
**Fix:** 404 (or explicit empty-with-event-check) on unknown events; accept an optional `now` in the list path or document the drift as tolerated.

## 4. Positive Observations

- **The shared-predicate architecture is the right spine for AC-15.** Extracting `submissionStatusPredicate`/`submissionTaskPredicate` and generating the stage counts *and* the list filters from the same SQL fragments makes tile/destination agreement structural rather than coincidental — the strongest possible footing for "every count opens the work behind it." The doc comment on the predicate states exactly this contract.
- **The AC-15 test is genuinely good**: it enumerates every link the snapshot emits (pipeline, format mix, track pressure, waves, metrics), fetches each destination through the real router, and asserts cardinality equality — behavior, not implementation. The AC-14 test's mutate-then-refetch across status, format, and track is likewise a real DB-driven liveness proof at the API tier.
- **Auth is done properly**: `grants: ["program:read"]` with the `read` rate bucket, matching the submissions-route convention — the plan review's access-control recommendation was adopted, avoiding a repeat of the MRQ-60 class of defect.
- **The route follows the manifest convention** (`*.routes.ts`, `defineApiRoute`, `apiRoutes` export, full response schemas), so it lands in the OpenAPI document and `check:api` parity by construction.
- **The fixture follows the established shadow-schema pattern** from `submissions-list.test.ts` rather than inventing a new one, and seeds a shape (private-scheduled vs published agenda items, overdue vs future tasks, an off-format rejected row) that exercises the trickier derived predicates.
- **The client state machine is honestly built**: stale data stays visible under a labeled error banner with retry, the empty state preserves the pipeline shape at zero, loading placeholders are fixed-geometry, and the effect cleanup clears the interval and aborts in-flight requests. It deserves the tests it didn't get.
- **UI craft rules are respected in the CSS**: tabular numerals on every changing figure, reserved min-heights, fixed grid geometry across states — consistent with the "elements never jump" rule.
