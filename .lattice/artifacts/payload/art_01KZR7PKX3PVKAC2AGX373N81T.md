# Code Review: MRQ-52 — Bulk-write audit guard

Reviewed at worktree HEAD `a3a3de6` ("MRQ-52 bulk path audit guard"). Diff: two new files, `tests/ac-claims/MRQ-52.json` and `tests/node/bulk-paths.AC-66-69.test.mjs`. Verification performed live: the new test passes standalone, `npm test` passes hermetically in 21.9s (within the 30s budget), `npm run trace:ac -- --ticket MRQ-52` runs clean, and the AC ownership claims in the manifest were cross-checked against `tests/ac-claims/MRQ-19.json` and `MRQ-12.json` (both accurate). The two routed findings were independently confirmed real: `src/routes/evaluation.routes.ts:699` expands one placeholder per selected `submission_ids` entry, and `src/routes/public-form-routing.ts:194` expands one per `trackIds` entry. `runBulkByIds` itself (`src/api/bulk.ts:135`) is clean — `json_each(?)`, single bind, no expansion.

## 1. Verdict

**FAIL (implementation-level)** — The plan is sound and most of it is delivered well, but the guard does not meet the plan's own contract for what it must catch. Plan step 6 (authoritative, post-review-cycle) requires the guard to fail on "a new direct placeholder expansion" and "a new ID-set bulk writer that bypasses the helper." The delivered guard detects placeholder expansion only inside eight pre-named function scopes, and only in one of the two idioms this codebase actually uses. A new bulk writer in a new file — the exact Trap-11 recurrence this audit exists to prevent — passes the guard untouched. The fix is cheap and contained to the test file; the task should return to `in_progress`.

## 2. Summary

The audit's manual inventory work is genuine and its two routed D1-cap findings are real and correctly allowlisted by operation identity rather than line coordinates. The AC manifest is exemplary: `owns: []`, exercised criteria only, ownership attributions verified correct. The gap is future-proofing: the guard is an allowlist over known seams rather than a detector of new bypasses, so it gives standing assurance it cannot back.

## 3. Issues

**[MAJOR] tests/node/bulk-paths.AC-66-69.test.mjs:277 — Guard cannot detect a new bulk writer outside the eight named scopes**
`directPlaceholderFindings` is computed from `Object.entries(scopes)` — only the eight inventoried functions. A brand-new route or job file that hand-rolls `WHERE id IN (${ids.map(() => "?").join(",")})` is invisible to this check, and the `helperCalls` assertion at line 314 only notices new *callers of the helper* (the safe direction), not writers that bypass it. The plan explicitly requires the guard to fail on "a new direct placeholder expansion, a new ID-set bulk writer that bypasses the helper" — a bypass by definition appears outside the existing seams, so scanning only known scopes cannot satisfy this.
**Fix:** Add a repo-wide sweep over all `src/**/*.{ts,tsx}` modules (the test already loads them all in `loadModules`) that flags both placeholder-expansion idioms anywhere, checked against an explicit allowlist of known sites with their classification (see next two issues for what belongs on it). A new site then fails with "unclassified placeholder expansion — re-audit," which is exactly the contract the plan states.

**[MAJOR] tests/node/bulk-paths.AC-66-69.test.mjs:212 — `dynamicPlaceholder` misses the codebase's dominant expansion idiom**
The regex `/\$\{[\s\S]*?\.map[\s\S]*?["']\?["'][\s\S]*?\}/` only matches when `.map(() => "?")` sits inline inside the template interpolation. The prevailing idiom in this repo hoists it: `const placeholders = ids.map(() => "?").join(","); ... IN (${placeholders})` — see `src/lib/venues.ts:136`, `src/routes/tokens.routes.ts:75`, `src/routes/submissions.queries.ts:353`, `src/routes/agenda.queries.ts:413`, and `src/routes/evaluation.routes.ts:635`. A new expansion written in the house style — even inside one of the eight guarded scopes — evades detection entirely. (The two allowlisted findings happen to use the inline form, so their *removal* still fails loudly; only *additions* slip through.)
**Fix:** Detect the hoisted form too — simplest robust predicate: match `.map(` with a `"?"`-producing callback anywhere in the scope (`/\.map\(\s*\([^)]*\)\s*=>\s*["']\?["']/`), or AST-match CallExpressions of `.map` whose body is the string literal `"?"`. Combined with the repo-wide sweep above, both idioms are covered.

**[MINOR] tests/ac-claims/MRQ-52.json:5 — "The two D1-cap bypasses" reads as a repo-wide completeness claim the artifacts don't record**
Within the named bulk-write families the two-findings claim is accurate. But `src/` contains roughly ten other ID-set placeholder expansions (files listed in the previous issue, plus `src/routes/submission-record.routes.ts:419,447` and `src/routes/public-form.routes.ts:365,645`), and the audit records no classification of them anywhere. Most are plausibly bounded reads (track sets, attachment sets, page-bounded rows), but one deserves a routed observation: `addDraftMetadata` (`src/routes/submissions.queries.ts:353–354`) binds one placeholder per draft-submission row, and its missing-fields-queue caller at line 420 appears to fetch rows before pagination is applied (`items.slice(page.offset, ...)` at line 424) — at scale that is a candidate D1 100-parameter hit on a read path. It is outside this ticket's bulk-*write* families, so it is not a scope violation, but the plan's inventory requirement ("classify each write... keep fixed-binding work explicitly documented") is best satisfied by putting these sites on the allowlist with a one-line classification each, which the repo-wide sweep needs anyway.
**Fix:** Fold the classification into the new allowlist (site → bounded-by reason), soften the manifest note to "the two D1-cap bypasses *on named bulk-write paths*," and route the `addDraftMetadata` observation to the Orchestrator with the reproduction boundary.

**[MINOR] tests/node/bulk-paths.AC-66-69.test.mjs:192–204 — `callsNamed` counts only bare-identifier calls**
An aliased import (`import { runBulkByIds as bulk }`) or namespace call (`bulk.runBulkByIds(...)`) is not counted, so a legitimate new caller could appear without the caller-list assertion noticing. Low likelihood, but the guard's value is exactly in the unlikely cases.
**Fix:** Also match `ts.isPropertyAccessExpression(node.expression)` with `.name.text === name`, and assert against import specifiers rather than call-site identifiers if aliasing ever appears.

**[MINOR] tests/node/bulk-paths.AC-66-69.test.mjs:314–319 — Caller-list assertion fails on safe growth with a misleading message**
`helperCalls` expands by call count, so a second legitimate `runBulkByIds` call inside `evaluation.routes.ts` fails `deepEqual` with "must retain one shared runBulkByIds seam" — but the seam *was* retained. Forcing a re-audit on any new call site is a defensible policy; the message just misstates what happened.
**Fix:** Reword the assertion message to say new-or-removed helper call sites require re-auditing this allowlist, matching the style of the placeholder-findings message at line 301.

## 4. Positive Observations

- **The positive-control discipline is excellent.** Every named scope is asserted non-null, and the content assertions (`writeBulkSubmissionDecisions` must reference `insertDecisions`, `recipientsFor` must contain `json_each(?)` and `return []`, `promoteRound` must call `runBulkByIds`) make an empty or dead inventory unable to pass — exactly what the plan's step 1 demanded, and a discipline many guard tests skip.
- **Allowlisting findings by operation identity rather than coordinates** is the right shape: refactoring line numbers doesn't break the guard, but silently *fixing or removing* either routed finding fails `deepEqual` and forces a fresh audit. The paired assertion on the uncapped `submission_ids: z.array(...).min(1).optional()` selector (verified present at `src/routes/evaluation.routes.ts:68`, alongside the capped variant at line 82) keeps the second scale hazard visible.
- **The AC manifest is a model citizen**: `owns: []` as the plan required, exercised-only claims, and the ownership attributions (AC-66–69 → MRQ-19, AC-117 → MRQ-12) are correct against the actual manifests — I verified both.
- The `typescript-ast` npm alias resolves to the real `typescript@5.9.3` compiler (pre-existing devDependency), the whole suite stays hermetic and inside the 30s budget with the new test included, and the self-recursion and single-export checks on the helper (`lines 313, 320–322`) close off two subtle seam-duplication routes.
