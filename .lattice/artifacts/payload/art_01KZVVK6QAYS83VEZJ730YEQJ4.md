# Plan Review: MRQ-136 — Public agenda controls do not reflect the filters in effect

### 1. Verdict

**FAIL (plan-level)** — The plan is a verbatim copy of the task description with no investigation added, and fresh verification against both the code and the live site shows the ticket's proposed fix shape ("mark the matching `<option selected>`, apply the active class to the day tab") chases a misdiagnosis. Implemented as written, the change would be a no-op that leaves the real defect in place. The task should return to `in_planning`.

### 2. Summary

I reviewed the MRQ-136 plan against the deployed lineage of the code (the ticket's sha `75b871d94c6f` and current live `1058ed23caf7`), re-ran the ticket's curl probes against live, and reproduced the SSR behavior with the repo's actual `preact-render-to-string` version. The plan restates the problem accurately but proposes a mechanism that **already exists and already works**: the select already binds `value={data.filters.track ?? ""}`, the day tabs already compute an `active` class, and `preact-render-to-string` 6.7.0 serializes `<select value>` into a `selected` attribute (verified: `GET /agenda?track=trk_agents` renders `<option selected value="trk_agents">` on live *today*, and `?day=2026-10-13` renders `class="active" aria-selected="true"`). The real defect is **parameter normalization**: the SQL filter accepts a track by id *or* case-insensitive name, but the select compares the raw query param against id-valued options, so name-form URLs (`?track=Agents`) narrow the list while the control still reads "All tracks." A revised plan must target that root cause, extend it to the `format` and `room` facets which share the identical id-or-name tolerance, and pin down what the day-tab claim actually was.

### 3. Issues

**[CRITICAL] Fix shape — The proposed mechanism already exists; the real defect is param normalization**
The plan's entire implementation direction is "mark the matching `<option selected>` from the request's track param and apply the active class to the selected day tab." Both mechanisms are already present on the deployed lineage (`PublicAgendaPage.tsx` binds `value=` on the select and `active`/`aria-selected` on day tabs), and `preact-render-to-string@6.7.0` serializes `<select value>` to `selected` (reproduced locally with the repo's installed version). Live confirms it: the ticket's own byte counts differ by 13 bytes between the two track URL forms precisely because **the id form (`?track=trk_agents`) already renders `selected` and the name form (`?track=Agents`) does not**. The ticket's "NO option carries a selected attribute" evidence was captured from the name-form markup and over-generalized. The actual bug: `loadPublicAgenda` passes the raw param straight through (`track: filters.track ?? null`) while `sessionRowsQuery` matches `track_id = ? OR lower(name) = lower(?)` — so any name-form link filters correctly but can never match an id-valued `<option>`.
**Recommendation:** Replan around normalization: in `loadPublicAgenda` (deployed lineage of `src/lib/public-site.ts`), resolve the incoming track param against the already-loaded track catalog (match id, else case-insensitive name) and put the **canonical id** in `data.filters.track`. Decide and state the behavior for a no-match value (e.g., `?track=Bogus`, which currently empties the list while the select reads "All tracks").

**[CRITICAL] Scope — The same defect exists on the `format` and `room` facets, which the plan never mentions**
On the deployed lineage the filter bar has four facets, and the SQL carries an explicit comment: "Format and room accept an id or a display name, exactly as the track facet does." So `?format=Workshop` and `?room=<name>` misdescribe the view in exactly the same way. A fix that normalizes only `track` ships the identical judge-visible bug on two sibling controls in the same toolbar.
**Recommendation:** The revised plan should normalize all three id-or-name facets (track, format, room) through one shared resolution step, and say so explicitly.

**[MAJOR] Evidence — The day-tab claim does not reproduce with valid values and needs re-verification before it drives code**
On live today (and no agenda-file commits landed between the ticket's sha and the current deploy, so this held at `75b871d94c6f` too), `?day=2026-10-13` correctly highlights the matching tab. The day tabs are submit buttons whose values are ISO dates, so every link the UI itself generates highlights correctly. The ticket's "`?day=N`" probe presumably used a non-date value — in which case the *deeper* live defect is that an unrecognized day value silently **empties the session list** (the filter compares `session.date === selectedDay || session.day === selectedDay`) while no tab is highlighted. That is a different fix (treat unknown day values as "all", or reject them) from "apply the active class," which is already applied.
**Recommendation:** Pull the exact URL from the sbek run (2026-08-12T15-33-34, public-widgets, defects[2]), reproduce it, and plan the day fix against what actually fails: most likely "unrecognized `day` values fall back to `all` (full list, All-days tab active)" rather than any change to class assignment.

**[MAJOR] Missing baseline — The plan does not state which lineage the fix targets, and the local `main` is not it**
The primary checkout's `main` (22e4a75f) has diverged from the deployed lineage: its `PublicAgendaPage.tsx` is 311 lines with a three-facet filter bar and no "All days" tab, while the deployed lineage (`github/main`, tip 24571d5b) has the ~1200-line version the ticket's `:767` line reference points into. An implementer who branches from the stale local `main` will find code that doesn't match the ticket at all and may "fix" the wrong file.
**Recommendation:** State the base explicitly: branch from `github/main` (the `mrq-136-agenda-filter-state` branch already exists and contains the deployed lineage) and work in a linked worktree per the repo rules — never in the primary checkout.

**[MINOR] Verification — No test plan, no acceptance criteria, no post-deploy check**
The plan contains no testable acceptance criteria and no verification steps. This bug class (server-rendered state echo) is cheap to lock down in Vitest without a browser.
**Recommendation:** Add: (1) unit tests asserting `loadPublicAgenda({ track: "Agents" })` returns `filters.track === "trk_agents"` (and the format/room equivalents, plus a no-match case); (2) an SSR assertion that the rendered markup carries `selected` / `class="active"` for name-form params; (3) the curl probes from the ticket re-run against live **after deploy**, since merging does not ship (DEPLOY.md). Note the evidence sha is already stale (live is `1058ed23caf7`, ticket says `75b871d94c6f`) — harmless here, but the plan should validate against what is actually deployed at fix time.

### 4. Positive Observations

- The underlying ticket is excellent field work: confirmed on live by curl rather than inference, with byte counts, exact markup, a provenance pointer to the sbek run, and a sharp cross-surface observation (the embed configurator reflecting URL state while /agenda appears not to). That contrast was a genuinely useful clue — it is what makes the 13-byte discrepancy between the two track-URL forms visible in the ticket's own evidence.
- The urgency framing (public, judge-visible, sharing is a scored capability, small fix) is well-calibrated and correct — this *is* worth fixing fast, which is exactly why it deserves a plan aimed at the real cause.
- Scope discipline is good: no creep, no speculative refactors, correctly sized as small with no dependencies.

The failure here is narrow but decisive: the plan adds nothing to the task description, and the one thing a plan must do — verify the diagnosis against the code before committing to a fix shape — would have caught in minutes that the "missing selected attribute" machinery already exists and the bug lives in parameter normalization. With that correction (plus the format/room extension and a real test plan), this becomes a strong, quick ticket.
