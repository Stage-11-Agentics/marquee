# Plan Review: MRQ-103 — Theme system (Day default + night candidates + Vaporwave)

### 1. Verdict

**FAIL (plan-level)** — The plan is a verbatim copy of the task description. The description itself is unusually spec-like and technically sound, but a plan that adds zero decomposition, sequencing, verification strategy, or codebase-grounded detail gives no evidence the implementer has engaged with the work. The gaps below are cheap to close in one revision pass; the task should return to `in_planning`.

### 2. Summary

Reviewed the MRQ-103 plan against the task description, the live repo (prototype at `prototypes/pipeline-v1.1/index.html` — 3,457 lines, ~88 raw hex occurrences matching the "~85" claim; `src/styles/tokens.css` and `components.css` exist; `check:design` → `scripts/checks/verify-design-contract.mjs`), and project conventions. The underlying directive is excellent — architecture chosen, scope fenced, risks named — but the plan document contributes nothing beyond it. The key concern is the missing execution layer: how Phase 1 will be sequenced, verified, and handed to the operator gate, and how the mid-ticket operator decision (night-winner pick) is represented in the ticket lifecycle.

### 3. Issues

**[CRITICAL] Whole plan — Plan is the task description, verbatim**
Every line of the plan already exists in the description; nothing is added. A plan's job is to show the implementer has turned intent into steps: work order within Phase 1 (machinery first? switcher first? one theme end-to-end as the template, then the others?), what "done" looks like per step, and what was learned from actually opening the target files. As written, plan review can only re-review the directive — the stage adds no verification value and implementation begins with no committed approach to hold it accountable.
**Recommendation:** Rewrite the plan as an ordered step list with per-step outputs. Suggested skeleton: (1) tokenize the ~88 raw hex in the prototype into `:root` (this is a prerequisite, not "as encountered" — see next issue); (2) build the `data-theme` override machinery + THEMES registry + localStorage persistence; (3) build the fixed-width top-bar switcher and verify no layout shift; (4) author Night candidate A end-to-end including contrast comments and track-color octaves, as the template; (5) Nights B and C; (6) Vaporwave; (7) self-review pass against Flight Deck craft rules; (8) operator gate. Phase 2 planned only in outline, explicitly blocked on the gate.

**[MAJOR] Phase 1 — "Tokenized as encountered" understates a hard prerequisite**
Theme overrides via `html[data-theme]` custom-property blocks only affect colors that are consumed *through* custom properties. Any of the ~88 raw hex values left un-tokenized is invisible to every theme — it will render as a Day-colored artifact inside Night/Vaporwave. "As encountered" implies incremental, optional cleanup, but for the four new themes to be judgeable at the design gate, tokenization of effectively *all* color-bearing hex in the prototype is step zero, not a side effect.
**Recommendation:** Promote tokenization to an explicit first step with a completion check (e.g., grep for `#hex` outside the `:root`/theme blocks returns only a deliberate, listed allowlist — the same rule Phase 2 will later encode in `check:design`, dry-run early).

**[MAJOR] Lifecycle — The mid-ticket operator gate has no representation in the plan**
Phase 2 is blocked on the operator picking a night winner, and the directive separately warns "do not merge near the submission window without operator go-ahead." The plan doesn't say how this pause is handled: does the ticket sit in a waiting status with a comment requesting the pick? Is Phase 1 its own PR (reviewable, un-merged) with Phase 2 a follow-up commit on the same branch? With a fleet sharing this board, an unstated gate is how a ticket silently stalls or, worse, self-approves.
**Recommendation:** State the mechanics: open the Phase-1 PR as the design-gate artifact, post a Lattice comment tagging the operator with a link and the three-candidate summary, hold the ticket out of `done`, and resume Phase 2 only on a recorded pick. Also state the merge posture explicitly (expected: no merge before the 2026-08-12 22:00 PT submission window without go-ahead).

**[MAJOR] Verification — No verification strategy for any of the graded claims**
Three claims in the directive are checkable but the plan names no method: (a) contrast — "ratios in comments, nothing under 4.5:1" needs a measurement method (a small script or documented tool run), or the comments are unverifiable assertions; (b) "elements never jump" — the fixed-width switcher needs an actual check (toggle through all five themes, confirm zero layout shift, ideally via the embedded browser); (c) the Phase-2 `check:design` no-raw-hex rule needs a plan for the allowlist contents and a note that the addition stays inside the 45s suite / 120s gate budgets.
**Recommendation:** Add a "Verification" section covering all three: how ratios are computed, how no-jump is demonstrated (screenshot or scripted toggle pass), and how the new check rule will be tested (known-bad fixture fails, current tree passes, runtime measured).

**[MINOR] Branch/worktree — Branch name inconsistency**
The plan says branch `mrq-themes`; the task's `branch_links` already records `mrq-103-themes` (linked by `agent:claude-theme`). Small, but in a multi-agent tree two half-real branch names is how work lands in the wrong place.
**Recommendation:** Reconcile to one name in the plan (presumably `mrq-103-themes`, since it's already linked) and confirm the worktree path under `../Marquee-worktrees/`.

**[MINOR] Phase 2 — No FOUC/first-paint note for the app switcher**
In the app, applying a persisted theme from localStorage after framework mount produces a Day-colored flash on every load for non-Day users — exactly the kind of transition defect this project grades (R7, "any slow list or transition is a defect"). The prototype (single static HTML file) dodges this; the app won't.
**Recommendation:** One line in the Phase-2 outline: read localStorage and set `data-theme` in a tiny inline script before first paint.

### 4. Positive Observations

- **The directive is spec-quality.** The architecture is decided, not deferred: palette-only overrides under `html[data-theme]`, structure tokens theme-invariant, one CSS block + one registry row per theme. That's the right shape — it keeps Day provably untouched and makes extensibility a property of the design rather than a promise.
- **Scope is fenced with unusual discipline.** Day untouched as default, no `prefers-color-scheme` auto-switch, three night candidates explicitly disposable, Vaporwave scoped as an extensibility proof rather than a feature. The "operator picks ONE, others deleted before the app fold" rule pre-empts theme sprawl.
- **Risk posture is real.** Linked-worktree isolation from the live fleet, the acknowledged DESIGN.md override, the ~22h runway acknowledgment, and the merge freeze near the submission window are all named up front.
- **The quantities are honest.** The "~85 raw hex" claim measures at ~88 in the actual prototype; the file paths (`prototypes/pipeline-v1.1/index.html`, `src/styles/tokens.css`, `components.css`, `check:design`) all exist as described. Whoever wrote the directive read the tree.
- **Rot prevention is designed in.** Extending `check:design` with a no-raw-hex rule turns the tokenization from a one-time cleanup into an enforced invariant — the difference between a theme system that works today and one that still works in a month.
