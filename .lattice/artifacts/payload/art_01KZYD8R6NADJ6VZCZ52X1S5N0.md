## 3. Issues

**[MAJOR] src/lib/speaker-membership.ts:4-15 — bridge docstring is now factually wrong about its own callers**
The docstring states `memberships(role='speaker')` is written from exactly two places: "an organizer adding them to the roster (the only way a speaker with no session exists)" and "the acceptance boundary." This PR adds a third caller — `importSpeaker` in `sessionize-import.ts` — without touching this comment. Two claims are now false: the caller count, and the parenthetical "(the only way a speaker with no session exists)," since a speakers-only import now also creates a speaker with no session via this exact path. This is the identical failure mode the ticket description itself names when describing the *bug* ("The bridge docstring names the four surfaces that break without the row... The import is a third place a person becomes a speaker of the conference and does not call the bridge") — now that the import *does* call the bridge, the docstring needs the update it was implicitly promised. It's also the same category of defect this branch's neighbor commit (MRQ-161, `tests/integration/api/meta.test.ts`) exists to eliminate: a comment telling a reader something about the codebase that isn't true.
**Fix:** Add the import as a third bullet under "the row is written where a person becomes a speaker of this conference," e.g. "— the Sessionize speakers import, for every reconciled row regardless of whether the person record itself changed," and drop or qualify "(the only way a speaker with no session exists)" since it's no longer exclusively true of organizer hand-add.

## 4. Minor Issues / Suggestions

**[MINOR] src/lib/sessionize-import.ts:169, 253, 256, 541 — `ImportSnapshot.membership` is write-only, never read**
The `membership?: MembershipRow | null` field (comment: "records the membership this row owned") is populated in the race-loser branch (line 541) but never consulted by `restoreSnapshot` or `removeImportedSpeakerMembership` — only `membership_created` and `membership_id` drive undo behavior. It's harmless (extra JSON bytes in `before_json`) but the comment implies a functional role it doesn't have, which will mislead the next reader into thinking undo depends on it.
**Fix:** Either drop the `membership` field entirely (nothing currently reads it), or if it's meant as forward-looking documentation of the pre-existing row for a future feature, say that explicitly instead of "records the membership this row owned."

**[MINOR] tests/integration/api/sessionize-import.AC-110-113.test.ts — the "skipped outcome, newly-bridged membership" branch is exercised implicitly, not directly**
The code correctly calls `speakerMembershipStatement` unconditionally, independent of the created/updated/skipped `outcome` classification (`sessionize-import.ts:527-537`), and the undo path independently checks `membershipCreatedMarker` regardless of `row.outcome` (`sessionize-import.ts:952-954` region). This is good — it fixes the bug for the case of an org-level person who already matches all CSV fields but has never joined *this* event's roster, which is arguably the most realistic recurrence of the original symptom (an organizer imports a known speaker into a new event). But no test row hits exactly that combination: the "Pre-existing Import Speaker" fixture is skipped *and* already has a membership (so `membership_created` stays false), while the two membership-creating rows in the test ("Dana" and "Updated Import Speaker") are `created`/`updated`, not `skipped`. The skipped+membership-created interaction is covered only by code inspection, not by an assertion.
**Fix:** Add one more fixture person — pre-existing in `people`, fields identical to their CSV row, but with no seeded `memberships` row for `EVENT_ID` — and assert both that the run reports `skipped` for that row and that undo still removes the membership it created.
