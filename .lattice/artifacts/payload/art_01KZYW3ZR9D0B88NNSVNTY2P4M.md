# Plan Review: MRQ-181 — Fresh magic link burned by an existing session

## 1. Verdict

**FAIL (plan-level)** — The plan section is a verbatim copy of the task description, not a plan. It contains no root-cause hypothesis, no file inventory, no implementation approach, and no test design. Worse, the one place it *does* diverge from the task is a constraint rewrite that replaces the fleet's shared gate lock with a private lock that serializes with nobody.

## 2. Summary

I reviewed the MRQ-181 plan against the task description and against the live codebase (`src/routes/auth.routes.ts`, `src/lib/auth/magic-links.ts`, and the fleet's `gate-lock.sh`). The task is well-specified and legitimately scoped; the plan adds zero information to it — every section from "The judge's own words" through "Acceptance" is copied character-for-character. The key concern is that this ticket's central engineering question — *by what mechanism does a pre-existing session cause the exchange to fail?* — is genuinely non-obvious from the code (the handler never checks for an existing session), and the plan neither answers it nor acknowledges it needs answering.

## 3. Issues

**[CRITICAL] Entire plan — It is the task description, not a plan**
Lines 64–103 of the plan reproduce the task description verbatim. There is no design work: no statement of where the defect lives, no proposed code changes, no list of files to create or modify, no UI approach for the "way out" screen, no test plan beyond restating the acceptance criteria. A plan review cannot evaluate feasibility, architecture, or risk when the plan expresses no decisions to evaluate. Restating the requirements demonstrates the requirements were received, not that anyone knows how to meet them.
**Recommendation:** Return to `in_planning`. The revised plan must contain, at minimum: the root-cause finding (see next issue), the files to be touched, the mechanism by which the token survives a blocked exchange, the three-cause messaging design, the way-out screen design, and the shape of the regression tests.

**[CRITICAL] Constraints §gate — The gate-lock constraint was rewritten into a lock that serializes with no one**
The task constraint says: route every `pr-gate`/full-`npm test` run through `/Users/atin/Projects/Stage11/deployments/Marquee-worktrees/.gate-lock/gate-lock.sh`. The plan replaced this with a Python `fcntl.flock` one-liner on `/tmp/marquee-gate.lock`. I read `gate-lock.sh`: it is a **mkdir-based lock on `Marquee-worktrees/.gate-lock/held`** — a completely different primitive on a completely different path. A run under the plan's flock acquires its private lock instantly, lands on top of whichever fleet agent currently holds the real lock, and inflates that agent's gate time past the 120s budget — the exact failure mode the fleet rule exists to prevent ("a lock only serializes its participants"). The task constraints also carry the timeout-vs-red guidance (`uptime` check, CI as tonight's oracle), which the plan dropped.
**Recommendation:** Restore the constraint exactly as the task states it: all gate and full-suite runs go through `gate-lock.sh`, and a red under load is checked against `uptime` before being believed. Delete the flock one-liner.

**[MAJOR] What to build §1 — No root cause identified, and the code says the mechanism is not where the plan assumes**
I read the exchange handler (`src/routes/auth.routes.ts:271-301`). It does **not** check for a pre-existing session: it consumes the link via `consumeMagicLink` (atomic single-use UPDATE in `src/lib/auth/magic-links.ts:106-131`), then unconditionally creates a new session and sets the cookie. So "if a pre-existing session blocks the exchange, don't consume the token" presumes a blocking check that does not visibly exist in the handler — the pre-existing-session failure the judge observed must arise elsewhere (the `public`-route credential pipeline, `dropRejectedSessionCookie`/`credentialRejected` interplay, cookie-set ordering, or something in the redirect target). Until the actual failing path is located and named, the ordering fix in step 1 cannot be designed, and there is a real risk the implementer "fixes" a path that was never the one firing.
**Recommendation:** The plan's first work item must be a reproduction + trace: mint a link, hold a second session, walk the request through the auth middleware and handler, and write down the exact line where it diverges to `rejectMagicLink`. The fix design follows from that finding, not the other way around.

**[MAJOR] What to build §2–3 — No design for the three-cause messaging or the way-out screen, though both cut across API and frontend**
Today `rejectMagicLink` (`auth.routes.ts:47-54`) collapses *every* failure — missing token, expired, re-used, wrong purpose — into one redirect, `/signin?reason=expired`, and `consumeMagicLink` returns a bare `null` for all of them, so the caller cannot currently distinguish the three causes the acceptance criteria require. Meeting AC-2 therefore means changing the `consumeMagicLink` return contract (or adding a pre-check), adding at least one new `reason` value threaded through to the `/signin` page copy, and building the way-out screen with its two actions ("sign out and continue with this link" — which requires the token to survive *and* be re-presentable — and "continue as the signed-in person"). None of this is designed: no reason taxonomy, no frontend files named, no answer to how the retry keeps hold of the single-use token, no note on the "elements never jump" constraint for the swapped copy.
**Recommendation:** The plan should enumerate: the new distinguishable failure causes at the `consumeMagicLink`/handler boundary; the `reason` values and their exact `/signin` copy (three causes, three sentences, per the task); the way-out screen's location and its two actions including how the sign-out-and-retry path re-presents the surviving link; and the frontend files touched.

**[MAJOR] What to build §4 — The single-use-consumer audit has no enumeration**
The task asks that the reasoning be checked for *every* consumer of a single-use token. Grep shows `auth/exchange` referenced from `speaker-invites.routes.ts`, `public-form.routes.ts`, and `evaluation.routes.ts`, and the handler comment names `/api/v1/claim` as the separate exchange door for `claim` and `org_invite` links; `draft_resume`, `cospeaker_profile`, and `task_link` purposes all flow through this same handler. The plan neither lists these nor says which are in scope, so "fixed once rather than three times" is unverifiable.
**Recommendation:** The plan lists each single-use consumer (login, draft_resume, cospeaker_profile, task_link via `/api/v1/auth/exchange`; claim and org_invite via `/api/v1/claim`; any invite acceptance path), states for each whether the pre-existing-session hazard applies, and scopes which are fixed here versus explicitly deferred.

**[MINOR] Acceptance / testing — No test design, and the fails-on-main property needs care**
The constraint requires a regression test that fails on `main` and passes on the branch. The plan restates the acceptance criteria but doesn't say how the pre-existing-session condition will be reproduced in a test (it depends on the root-cause mechanism — a unit test against the handler may not exercise the middleware path where the defect actually lives). If the failing path is in the credential pipeline, the test must run through the same pipeline or it will pass on `main` and prove nothing.
**Recommendation:** Once the root cause is located, state the test vehicle (route-level test through the real middleware stack vs. unit test), and the four cases: fresh link + existing session (link survives, true reason shown), retry after sign-out succeeds with the same link, genuinely expired, genuinely re-used — each asserting a distinguishable message.

## 4. Positive Observations

- The task description embedded in the plan is excellent — the judge's observation is quoted verbatim, the two stacked failures are cleanly separated, and the acceptance criteria are concrete and testable (the fresh-link-survives property is exactly the right invariant to pin).
- The plan retains the full constraint block on worktree discipline, stash prohibition, migration stop-rule, and the deploy freeze — the operational guardrails (minus the gate-lock rewrite) made it through intact.
- Scoping item 4 (audit all single-use consumers) into this ticket rather than minting three follow-ups is the right call; the codebase confirms the same `consumeMagicLink` primitive serves multiple doors, so one fix at the primitive's contract genuinely covers them.

The task itself is ready; the plan in front of it is not. One planning pass that (a) traces the actual failure mechanism, (b) restores the fleet gate-lock constraint, and (c) names files, reason taxonomy, and test vehicle would very likely clear this review.
