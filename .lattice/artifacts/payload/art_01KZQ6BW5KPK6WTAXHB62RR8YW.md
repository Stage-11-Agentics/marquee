# Code Review: MRQ-3 — Auth, demo entry, and reset-demo

## 1. Verdict

**FAIL (implementation-level)**

The plan is sound and the fail-closed discipline (demo login, reset-demo, magic-link enumeration resistance) is implemented correctly everywhere I checked it directly. But I found two real, independently-verified defects that need fixing before merge: a delete-order bug in the reset-demo wipe that will throw a foreign-key violation and break AC-230's "never partially reset" guarantee the moment any `audit_log` row exists, and an open-redirect bypass in the magic-link `redirect_to` validator that the plan explicitly promised to close but didn't fully close.

## 2. Summary

Reviewed `src/lib/auth/*`, `src/routes/auth.routes.ts`, `src/routes/admin-ops.routes.ts`, `src/lib/reset-demo/*`, the `src/index.ts` wiring, `scripts/reset-demo.mjs`, and the three integration test files, cross-checked against `migrations/0001_init.sql`'s actual foreign keys and CHECK constraints rather than trusting the plan's claims. The AC-2 fail-closed proof, the AC-107 bearer/revocation flow, the AC-214 cross-event reviewer isolation, the magic-link single-use/expiry/hash-only-storage properties, and the outbox-only mail discipline (G3/A-3) are all implemented as designed and covered by tests I traced end-to-end against the schema. Two defects survive that trust-but-verify pass: `reseedDemo`'s `WIPE_ORDER` deletes `people` before `audit_log`, which references `people(id)` — the DELETE FROM people` statement will fail with a foreign-key constraint violation as soon as a demo session has generated any audit-log row, which is exactly the "mid-judging" scenario AC-230 is supposed to survive; and `isSafeRedirectTarget` only blocks `redirectTo` strings starting with `//`, missing the well-known backslash bypass (`/\evil.com`, which browsers implementing the WHATWG URL spec treat identically to `//evil.com` for special schemes), so the "kill open-redirect" claim in the plan is only partially delivered.

## 3. Issues

**[MAJOR] src/lib/reset-demo/reseed-demo.ts:16-44 (`WIPE_ORDER`) — `audit_log` is wiped after `people`, violating its own children-before-parents invariant**
The module's docstring says "Children-before-parents delete order for a full demo wipe," and every other table that references `people(id)` (`memberships`, `auth_sessions`, `magic_links`, `api_tokens`, `form_admins`, `outbox`, `submissions`, `submission_decisions`, `saved_views`, `participations`, `committee_members`, `reviewer_track_scopes`, `round_assignments`, `evaluations`, `comparisons`, `round_promotions`, `speaker_tasks`, `calendar_invites`) is correctly positioned before `people` in `WIPE_ORDER`. I checked `migrations/0001_init.sql` directly (`audit_log.actor_person_id TEXT REFERENCES people(id)`, line ~704) and confirmed `audit_log` is the one exception: it sits at index 41, three entries *after* `people` at index 38. Since the reseed runs the deletes as a single `db.batch()` (one D1/SQLite transaction, no `PRAGMA defer_foreign_keys` anywhere in the module), and SQLite enforces FK constraints per-statement unless deferred, `DELETE FROM people` will throw a foreign-key constraint failure the moment any `audit_log` row exists whose `actor_person_id` points at a person about to be deleted — which is exactly what accumulates during ordinary organizer/reviewer activity between resets. The whole batch then rolls back (D1 batch is atomic), so the reset silently fails and the queue consumer's catch block marks the job `failed` and retries the message indefinitely, since the same violation recurs every attempt. This directly undermines AC-230's "idempotent, safe mid-judging, never partially-reset" contract. It's currently latent only because no code path in the merged tree writes to `audit_log` yet (`src/db/schema.ts` defines the table but nothing inserts into it) — the moment audit logging ships, this breaks reset in production, unrecoverably, without a code change. None of the three `reset-demo.test.ts` cases insert an `audit_log` row before calling reset, so the suite doesn't catch it.
**Fix:** Move `"audit_log"` to before `"memberships"` (or anywhere earlier than `"people"`) in the `WIPE_ORDER` array. Add a regression test that inserts an `audit_log` row referencing a demo person before invoking `POST /api/v1/admin/reset-demo`, to lock the ordering in and catch the next table that adds a `people` FK without updating this list.

**[MAJOR] src/lib/auth/magic-links.ts:19-21 (`isSafeRedirectTarget`) — open-redirect protection is bypassable via the backslash trick**
The plan states this check exists specifically "to kill open-redirect," and the implementation blocks the literal `//` prefix — but browsers implementing the WHATWG URL Standard treat `\` identically to `/` when resolving a relative reference against a special scheme (http/https). A `redirectTo` value of `"/\\evil.com"` satisfies `startsWith("/")` and fails `startsWith("//")` (its second character is a backslash, not a slash), so `isSafeRedirectTarget` returns `true` and `mintMagicLink` accepts it without throwing. `authRoutes.get("/exchange", ...)` then does `context.redirect(link.redirect_to, 302)` with this value verbatim, and a browser resolving `Location: /\evil.com` against the app's own origin will treat it as protocol-relative and navigate to `https://evil.com`. This is reachable end-to-end from the unauthenticated, enumeration-resistant `POST /api/v1/auth/magic-link` endpoint: an attacker submits a real registered person's email with `redirect_to: "/\\attacker-controlled.example"`, the victim receives a legitimate sign-in email from the real domain (since delivery goes through the normal `outbox`/mail pipeline), clicks it trusting it, authenticates, and is then bounced off-site — a standard post-auth open-redirect phishing chain (CWE-601). No test in `auth-demo.test.ts` exercises `redirect_to` at all, so nothing currently guards this.
**Fix:** Normalize backslashes before checking, e.g. `redirectTo.startsWith("/") && !redirectTo.replace(/\\/g, "/").startsWith("//")`, or more robustly resolve via `new URL(redirectTo, "http://placeholder.invalid")` and assert `url.host === "placeholder.invalid"`. Add a test asserting `mintMagicLink`/`isSafeRedirectTarget` rejects `"/\\evil.com"` and similar variants.

**[MINOR] src/lib/auth/random-token.ts:5-11 (`mintToken`) — comment and design doc claim 256 bits of entropy; the actual output carries 192**
`TOKEN_BYTE_LENGTH = 32` draws 256 bits of true randomness via `crypto.getRandomValues`, but each byte is then reduced with `byte & 0x3f` to pick one of 64 base64url characters — this discards the top 2 bits of every byte, so the 32-character token actually encodes only `32 × 6 = 192` bits of the entropy drawn, not the 256 bits claimed by the inline comment (`// 256 bits of entropy per minted credential`), the ticket's Scope text ("Magic links (256-bit random...)"), and the plan's design decision #1. 192 bits is still astronomically more than sufficient for this purpose, so this is not an exploitable weakness, but the code doesn't do what its own comment and the binding spec text say it does.
**Fix:** Either encode using standard base64 (3 input bytes → 4 output chars, using all 24 bits) so 32 bytes genuinely yield ~256 bits of encoded entropy, or rename the constant/comment to reflect the true ~192-bit strength if the simpler per-byte encoding is intentional.

**[MINOR] src/routes/admin-ops.routes.ts:63-65 (`passesLocalValidation`) — token compared with `===` rather than constant-time**
Every other secret comparison this ticket introduces (`constantTimeEqualHex` in `random-token.ts`) is explicitly built to avoid timing side-channels, but the loopback-only local-validation header is compared with plain `===`. Impact is low — this path is loopback-only and the token is `undefined` (closed) in production per the code's own comment — but it's an inconsistency with the pattern the rest of the ticket establishes for exactly this class of comparison.
**Fix:** Reuse `constantTimeEqualHex` (or a plain-string constant-time compare) for the header check, for consistency if nothing else.

**[MINOR] src/routes/admin-ops.routes.ts:34-42 (`GET /reset-demo/:jobId`) — no authentication on job-status polling**
Unlike every other route this ticket adds, `GET /reset-demo/:jobId` has no auth check at all — anyone who obtains or guesses a job id can read its status/result. Impact is low (job ids are `crypto.randomUUID()`, ~122 bits, and `ReseedResult` only exposes row/table counts and a timestamp — nothing sensitive), so this is a nit rather than a real vulnerability.
**Fix:** Optional — gate this behind the same `passesLocalValidation`/`passesSessionScope` pair as the POST route for consistency, if the Orchestrator wants every admin-ops endpoint to share one auth story.

## 4. Positive Observations

- **The fail-closed discipline is real, not just asserted.** I traced `POST /api/v1/auth/demo`, `POST /api/v1/admin/reset-demo`, and `authMiddleware` directly: the demo-login and reset-demo routes both look up the `demo_mode = 1` event first and 403 with no cookie set if it's absent, exactly matching AC-2 and the plan's guardrail G6/A-5, and `authMiddleware` genuinely never rejects on its own — it only populates context, leaving `requireAuth`/`authHasRole` decisions to each route, which is the right shape for mixing public and gated endpoints under one `app.use("/api/*", ...)`.
- **Magic-link single-use/expiry is atomic and race-free.** `consumeMagicLink`'s `UPDATE ... WHERE id = ? AND used_at IS NULL AND expires_at > ?` checked via `meta.changes` is the correct pattern for eliminating a double-exchange race, and it's exercised directly by the "single-use" and "expiry" tests rather than only asserted.
- **Cross-event reviewer isolation matches the schema, not just the code's intent.** `roleForEvent`'s two-layer check (org-wide `event_id IS NULL` rows apply everywhere except for `reviewer`, which the schema `CHECK (role <> 'reviewer' OR event_id IS NOT NULL)` already forces to be event-scoped) is correctly reasoned and the accompanying `CONTRACT` tests assert both the general case and the CHECK-constraint rejection of an org-wide reviewer row, closing the loop between schema and application logic.
- **Auth mail discipline (G3/A-3) is structurally enforced.** `enqueueAuthMail` only ever inserts into `outbox` with `send_policy = 'demo_safe'`; no module under `src/lib/auth` or `src/routes` imports a mail provider, so the "queue consumer is the only sender" invariant isn't just a comment — it's an absence of any alternative code path.
- **The AC-2/AC-1 owns/exercises split in `tests/ac-claims/MRQ-3.json` is handled correctly**, and the AC-214 omission (per the documented plan-review resolution #5) is honored precisely — the reviewer-isolation test is titled `CONTRACT · reviewer scope does not cross events` without an `AC-214 ·` prefix, so it can't trip `trace:ac`'s unknown-criterion gate while still proving the behavior.
- **`reseedDemo`'s single-`db.batch()` transaction design is the right primitive for AC-230's atomicity requirement** — a concurrent reader genuinely sees old-state-or-new-state, never partial, for every table except the one ordering bug flagged above; the surrounding architecture is correct even though one entry in the list is wrong.
