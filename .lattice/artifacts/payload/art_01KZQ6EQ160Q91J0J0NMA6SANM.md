# Code Review: MRQ-14 — Uploads: presign, verify, and serve

## 1. Verdict

**FAIL (implementation-level)**

## 2. Summary

Reviewed `master...mrq-14-uploads` (branch `forgejo/mrq-14-uploads` @ `c6bb439`; the prompt's embedded diff was stale/truncated against an unrelated base, so this review is against the real 24-file, ~1,686-line diff computed from the current merge-base). The core presign→PUT→complete→serve pipeline for `draft_file` is well-built: trap 9 (custom-domain signing) and trap 10 (R2-only canonical URL) are defended with real tests, magic-byte sniffing is fail-closed with genuine container-manifest checks (not just a `PK` signature), origin isolation is correctly enforced and tested, and the ETag re-check on serve is a nice piece of defense-in-depth. All 55 tests pass in 8.3s (well inside the 30s budget), `tsc --noEmit` is clean on both tsconfigs, and `check:api`/`trace:ac` pass. However, the ticket's explicit, plan-review-authoritative scope was significantly and silently cut: the Cloudflare Images headshot-variant module doesn't exist at all, there is no sign route for `person_headshot` or `event_logo` (only `draft_file` and `task_upload` are wired), and two of the five required AC-231 table-driven guardrail cases are neither implemented nor tested. Plan-Review Cycle 1 resolution 11 explicitly anticipated this exact risk and required the delegator to **stop and ask the Orchestrator to split/extend the ticket** rather than silently ship without variants — that instruction was not followed.

## 3. Issues

**[CRITICAL] src/lib/r2/ — Cloudflare Images headshot-variant module was never implemented**
`src/lib/r2/images.ts` does not exist anywhere in the diff or the final tree (`find src -iname "*image*"` returns nothing; `grep -ri "cdn-cgi|variant"` only finds the unused `variants?` field in `protocol.ts:63`). This is explicit, verbatim ticket scope ("Images variants for headshots"), an explicitly required file in the Architecture section, and resolution 9 pinned the exact contract (`avatar`/`card`/`profile` derivatives via `/cdn-cgi/image/...`). Resolution 11 states in terms that leave no ambiguity: "Sweep and variants are still ticket scope and cannot be silently deferred because downstream tickets consume them. If the first stage exhausts the estimate, stop and ask the Orchestrator to split/extend the ticket rather than shipping an uncalled sweep or fake variant contract." The delegator shipped the sweep but silently dropped variants (self-acknowledged in the commit message as "deferred," but never escalated to the Orchestrator), which is precisely the action resolution 11 forbade. `CompletedUpload.variants` in `protocol.ts` is dead, unpopulated API surface.
**Fix:** Implement `src/lib/r2/images.ts` per resolution 9's frozen contract, wire it into `handleComplete` for `person_headshot` responses, or — if genuinely out of budget — stop and get the Orchestrator to split the ticket, per resolution 11's own instructions, rather than merging silently.

**[CRITICAL] src/routes/uploads.direct.ts — no sign route exists for `person_headshot` or `event_logo`**
Only two sign endpoints exist: `/api/v1/public/uploads/sign` (hardcoded to `draft_file` only) and `/api/v1/me/uploads/sign` (`uploads.direct.ts:236-242`, hardcoded to reject anything but `ownerType === "task_upload"` with the message "only task_upload is supported on this route in this window"). There is no authenticated/admin route for organizer-driven `event_logo` or `person_headshot` uploads at all, even though `policyFor` (`policy.ts:426-433`) fully implements their policy (including `HEADSHOT_MIN_DIMENSION`) and the Architecture section explicitly requires "handlers for public, speaker, and **authorized event/submission** sign/complete operations." This makes Local Verification §4 ("AC-52 upload-side tests: valid JPEG/PNG/WebP become ready...") entirely unexercisable — there is no code path to even create a `person_headshot` attachment. No test in the diff attempts a headshot upload.
**Fix:** Add the authorized event/person sign route for `person_headshot`/`event_logo`, or escalate per resolution 11 instead of merging with this owner-type scope silently cut.

**[MAJOR] src/lib/r2/complete.ts:65 — dimension floor only enforced for PNG, not JPEG/WebP**
`if (policy?.minImageDimension && (rule.kind === "png"))` — headshots explicitly allow JPEG/PNG/WebP (`policy.ts:375-380`) with a stated `HEADSHOT_MIN_DIMENSION`, but `sniff.ts` only implements `readPngDimensions`; JPEG/WebP dimension parsing is admittedly unimplemented ("tracked gap" comment in `sniff.ts`). An undersized JPEG or WebP headshot would pass verification and become `ready`, directly contradicting Local Verification §4 ("undersized or malformed images are rejected and deleted"). Currently unreachable in practice only because issue #2 above means headshots can't be signed at all yet — but this is exactly the kind of latent bug that ships live the moment someone wires the missing route without noticing the gap.
**Fix:** Implement JPEG SOF and WebP VP8/VP8L/VP8X dimension extraction (the plan explicitly called for "JPEG signature plus bounded SOF scan" and "WebP RIFF/WEBP chunk **and dimensions**" in the Architecture section), or block headshot completion for non-PNG kinds until it exists rather than silently accepting them.

**[MAJOR] tests/unit/r2/uploads-routes.test.ts — 2 of 5 required AC-231 table-driven cases are missing**
The Acceptance and trace ownership section names five required cases for the AC-231 guardrail test: missing/replayed/invalid Turnstile tokens (covered), missing authentication on a speaker/admin route (covered), **"a valid principal targeting another event/person/submission/task"** (not tested — the authorization check exists at `uploads.direct.ts` in the `/me/uploads/sign` handler, but there is no test where a valid session's speaker tries to upload against a task that isn't theirs), and **"a public request whose draft/field owner is out of scope"** (neither implemented nor tested — `fieldKey` is destructured and type-checked at `uploads.direct.ts:113,120` but never validated against the draft's actual event/form fields; any string is accepted).
**Fix:** Validate `fieldKey` against the draft's event/form-field scope before signing, and add both missing table-driven cases to the named AC-231 test.

**[MAJOR] src/index.ts:100 / src/routes/uploads.direct.ts — upload routes bypass the M-07 route manifest and OpenAPI registry entirely**
Confirmed empirically: `npm run check:api` on the branch reports only 2 registered operations (`GET /api/docs`, `GET /api/openapi.json`) — none of the 5 upload endpoints appear in the generated OpenAPI document at all, because `uploads.direct.ts` is deliberately named to dodge the M-07 manifest glob and mounted directly in `src/index.ts:100`. This was disclosed in the commit message as a deliberate deviation (M-07 merged mid-implementation), and `check:api` still reports `"status": "pass"` because it only checks internal consistency of what *is* in the manifest — but the ticket's own Local Verification §6 says to "Assert OpenAPI/runtime route parity comes from the generated M-07 registry," and that assertion cannot mean anything for a route set the registry doesn't know about. The public upload API is currently undocumented in the product's own OpenAPI spec, and `uploads.direct.ts` re-implements its own error envelope (`errors.ts`) and ad hoc session lookup instead of the merged M-07/MRQ-3 helpers the plan named as dependencies.
**Fix:** Port `uploads.direct.ts` onto the M-07 `defineApiRoute` contract (or file a tracked, orchestrator-visible follow-up ticket) before this is considered done — an unpublished write/read surface this large is a real product gap for a "kill my SaaS" competition entry whose API surface is part of the pitch.

**[MINOR] src/routes/uploads.direct.ts:147 — resume-token comparison is not constant-time**
`if (suppliedHash !== draft.resume_token_hash)` compares two hex SHA-256 strings with plain `!==`. Low practical exploitability (the attacker still needs the original resume token to have any use for a timing leak on its hash), but this module is otherwise unusually careful about closing exactly this class of gap.
**Fix:** Use a constant-time compare (e.g., a byte-wise XOR-accumulate or `crypto.subtle` based comparison) for both this and the completion-token check in `handleComplete`.

**[MINOR] package.json / vite config — resolution 10's client-bundle secret scan was not added**
Resolution 10 (accepted, rated MINOR) requires "a built-bundle scan that rejects signer module markers and every `R2_*`, `UPLOAD_TOKEN_SECRET`, and `UPLOAD_RATE_LIMIT_SECRET` binding name in client assets." No such script exists in `package.json` scripts or anywhere in the diff. `upload-client.ts` does correctly use `import type` only, so there's no live risk today, but the guardrail against a future accidental runtime import was not built.
**Fix:** Add a small post-build grep/scan step (can be cheap — `dist/client/**/*.js` grep for the binding names) wired into `check:api` or a new `check:*` script.

**[MINOR] tests/unit/r2/uploads-routes.test.ts — per-IP rate-limit boundary/reset is untested**
Local Verification §3 asks for "per-IP and per-submission cap boundary/reset returning 429." Only the per-submission cap (`AC-232 · per-submission upload cap returns 429...`) has a test; there's no equivalent for the per-IP cap despite `checkUploadRateLimits` implementing both symmetrically.
**Fix:** Add a per-IP boundary test (e.g., 21 requests across distinct submissions from the same `cf-connecting-ip`).

## 4. Positive Observations

- **Trap 9 and trap 10 are genuinely well-defended**, not just documented: `presign.ts` has both a static host-parsing test and a runtime "defense in depth" re-check (`presign.ts` throws if `signedUrl.hostname !== endpoint`), and `publicMediaUrl` structurally cannot return anything but the media origin.
- **Fail-closed magic-byte sniffing is correctly adversarial**: PPTX/KEY require their actual archive-manifest entry, not just a `PK\x03\x04` signature, and this is proven with a real adversarial-ZIP test (`policy.test.ts`).
- **The completion/serve race is handled thoughtfully**: `If-None-Match: *` on the signed PUT, plus a stored `r2_etag` that `serveMediaObject` re-checks against the live object's ETag before streaming — exactly the defense-in-depth resolution 8 asked for, and it's exercised end-to-end by the integration test (`uploads-routes.test.ts`'s "becomes ready and serves..." case).
- **Zero-side-effect ordering is correct and tested** for every AC-231 case that *is* covered — Turnstile/scope failures never reach the DB insert or the signer, and the tests assert `COUNT(*) FROM attachments === 0` rather than just checking the HTTP status.
- **Origin isolation is real, not just claimed**: the same integration test proves the media host returns 200 with `attachment`+`nosniff` headers while the identical path on the app host 404s.
- **Orphan sweep is correctly idempotent and safe under partial failure** — R2 delete before D1 row delete, with a missing object treated as already-deleted and a failed delete leaving the row for retry, matching the plan exactly. It's wired to the real `30 4 * * *` cron dispatch in `src/index.ts`.
- **Honest process hygiene**: `TODO-OPERATOR` markers in `wrangler.jsonc` are clear and correctly scoped to MRQ-57, and the deviations that were taken (route-manifest bypass, scope narrowing) were disclosed in commit messages rather than hidden — the issue is that disclosure without escalation isn't what resolution 11 asked for, not that the deviations were snuck in silently at the code level.
- **Empirically verified**: `npm test` (55/55, 8.3s), `tsc --noEmit` on both tsconfigs, `check:api`, and `trace:ac --scope=merged` all pass clean on the actual branch head.
