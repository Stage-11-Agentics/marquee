# Plan Review: MRQ-68 — Decided · not notified

## 1. Verdict

**FAIL (plan-level)**

The plan is very close — the strongest parts are verified accurate against the merged code — but the classification predicates that ARE this feature are left unstated, and as derivable from the plan's own text they misclassify two real decision states. A second stated decision (retry rows keyed by decision id) punches a hole in the merged acceptance-reversal suppression. Both fixes are a short, targeted revision of the plan text; neither requires re-research.

## 2. Summary

Reviewed the MRQ-68 plan (built-in `Decided · not notified` view, fourth attention-strip row, `Notify N speakers` head action; AC-268/AC-269) against the merged M-52/M-11 seams. The plan demonstrates unusually precise codebase knowledge — the `submission_decisions.outbox_id` association, the glob route manifest, the minimal-fixture `hasColumns` gating, and the immutable built-in-view pattern all check out against source. The key concern: the plan never states the per-reason predicates, and the residual case ("has address, no outbox row") is not uniquely "Changed in Airtable" — waitlisted decisions and template-disabled decisions both land there today.

## 3. Issues

**[MAJOR] Decisions and boundaries / Files §3 — The three-reason classification predicates are unstated, and the derivable residual misclassifies real states**
The whole ticket is "the Notified column must state WHICH reason applies," yet the plan specifies only the delivered predicate (associated outbox row is `sent`). The implied mapping is: `Not delivered` = associated row in `queued`/`suppressed`/`failed`; `No valid address` = no usable address; `Changed in Airtable` = the remainder (has address, no outbox row). But that remainder is not Airtable-only in the merged code: (a) **every waitlisted decision** has `outbox_id = NULL` by design (`src/jobs/cascade/decisions.ts:701–702` — waitlist enqueues no mail), and (b) an accepted/rejected decision made while the template is **disabled** also gets `outbox_id = NULL` (`enqueueTrigger` returns null at `src/jobs/mail/triggers.ts:28`, and the writer stores `mail.id = null`). Both would render "Changed in Airtable" — a wrong reason naming a feature Amendment 17 cut. The waitlist sentence ("Waitlisted rows remain on the existing M-52 semantics") gestures at this but never states the observable behavior: do waitlisted records appear in the view, the dashboard count, or the notify action at all? An implementer can read it either way, and one reading leaves every waitlisted record permanently in the gap view with an unsendable notify action (M-52 has no waitlist template).
**Recommendation:** Add an explicit predicate table to the plan: which decision `resulting_status` values are in scope (state plainly that waitlisted decisions are excluded from the view, the count, and the action — or whatever the choice is); the exact SQL-level discriminator for each of the three reasons; and how a null-`outbox_id` accepted/rejected decision that is *not* Airtable-origin (disabled template) is classified. Consider `submissions.last_write_source = 'airtable'` (AC-227 machinery, already on every row) as the positive discriminator for "Changed in Airtable" instead of inferring it from the absence of an outbox row.

**[MAJOR] Decisions and boundaries — Retry rows keyed by decision id escape the merged acceptance-reversal suppression**
The plan associates retry rows via `outbox.entity_id = decision id`. But the merged reversal path suppresses pending decision mail with `WHERE entity_id = <submission id> AND ics_body IS NULL AND status = 'queued'` (`suppressQueuedSubmissionEmails`, `src/jobs/cascade/decisions.ts:507–512`, `suppressed_reason = 'acceptance_reversed'`). A notify-retry row carrying the decision id will not match. Concrete failure: acceptance decided → original send fails → operator clicks "Notify N speakers" (new queued row, entity_id = decision id) → operator reverses the acceptance before the consumer sends → the retry acceptance email still goes out for a reversed decision, violating the exact invariant `acceptance_reversed` exists to protect. The decision-id association is otherwise a good choice (it keeps the delivered-derivation clean and unambiguous), so the fix belongs on the suppression side, not the association side.
**Recommendation:** State in the plan how reversal reaches retry rows — e.g., extend the reversal suppression to also match queued rows whose `entity_id` is any decision id for the reversed submission (a small, testable widening of the existing query), and add a fixture for reverse-after-retry-queued. If instead the team accepts the window as a known gap, the plan and PR body must say so explicitly rather than leave it implicit.

**[MINOR] Files §4 — "Calls the existing renderer/queue path" and "fresh idempotency key per explicit retry" are in tension**
The existing path derives the key internally and deterministically: `buildIdempotencyKey(templateKey, entityId, personId)` (`src/jobs/mail/outbox.ts:33–39`), and `EnqueueOutboxInput` has no key override. With decision-id as entityId, the *first* retry gets a fresh key for free, but a *second* explicit retry of the same decision dedupes onto the first retry row and silently sends nothing — which matters exactly when the first retry itself failed.
**Recommendation:** Name the extension in the plan: an optional idempotency-key override (or nonce input) on `enqueueOutbox`, and an AC-269-adjacent assertion that a second explicit notify after a failed retry inserts a new row.

**[MINOR] Verification — No fixture for the reversal-then-re-decide dedupe edge**
Because the original decision key is `sha256(template:submissionId:personId)`, a re-acceptance after reversal dedupes onto the *original* outbox row (`insertOutbox` unique-constraint path, `src/jobs/mail/outbox.ts:109–114`): if that row was suppressed, the new decision correctly surfaces as `Not delivered`; if it was already `sent`, the re-decision reads as delivered though no new mail carried its (possibly different) feedback. The view is the first screen that makes this pre-existing behavior visible, so the test suite should pin what it shows.
**Recommendation:** Add one fixture: decide → reverse (row suppressed) → re-decide, and assert the record appears as `Not delivered` with the `acceptance_reversed` suppressed-reason detail — this is also the happy path proving the notify action heals it.

**[MINOR] Files §2/§3 — Notified-column data availability outside the built-in view is ambiguous**
Step 2 extends the list item contract with notification state "on each row," while step 3 routes the derivation "through that joined query only" for `not_notified`. If the join only runs under the `not_notified` filter, a user adding the registry's `Notified` column to any other view gets an empty column; if it always runs, the minimal-fixture compatibility and the R7 speed budget for the default list are affected.
**Recommendation:** State the choice: either the column is populated in all views (join gated on table existence, with a note on list-query cost), or the column is exclusive to the built-in view and the registry/UI enforces that.

## 4. Positive Observations

- **The codebase claims verify.** `submission_decisions.outbox_id` exists and is written by the one decision writer (`src/db/schema.ts:385`, `decisions.ts:725`); the route manifest genuinely is a hand-edit-free glob so adding routes to `submissions-bulk.routes.ts` needs no registration (`src/routes/_manifest.ts`); the minimal-fixture concern mirrors the existing `hasColumns` gating pattern (`submissions.queries.ts:436`); the immutable built-in-view pattern from MRQ-34 is exactly where the plan says it is (`src/lib/saved-views.ts`). This is a plan written by someone who read the code, and it shows.
- **The zero-state row is handled with the right philosophy.** Unconditional fourth attention item, affirmative sentence at zero, reserved layout space — matching both AC-268's "not removed from the DOM" and the elements-never-jump rule, and consistent with the existing strip where `overdue_submissions` already renders unconditionally.
- **AC-269's byte-identical assertion is planned as written** — snapshotting `decision`, `decided_at`, `decided_by_person_id`, `feedback_md` before notify and proving exactly one new outbox row per sendable record, with no-address exclusion from both action and count. Full-fidelity AC coverage, explicitly tagged.
- **Amendment 17 is handled honestly** — retaining the contract-compatible "Changed in Airtable" reason while stating its theoretical status in detail copy, and naming the choice in the PR body rather than quietly reinterpreting the AC.
- **Deterministic latest-decision ordering (`decided_at DESC, id DESC`) and one shared derivation expression** across list, summary, and dashboard count prevents the three surfaces from ever disagreeing — the exact failure mode a gap-surfacing feature cannot afford.
- **Non-goals are crisp and correct**: zero schema honored, no contract-doc or prototype edits, no `always_live` changes, no new decision writer.
