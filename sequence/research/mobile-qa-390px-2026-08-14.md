# Marquee — Mobile QA (390px phone viewport)

Live site: https://marquee.stage11.dev · signed in via `?demo=organizer`
Viewport: 390 css px wide (373px content width after a 17px classic scrollbar), dpr 2.
Shots: `mobile-qa-shots/`

**Excluded by brief (known/being redesigned):** the ≤760px bottom nav strip itself, and
the conference switcher / sidebar footer being unreachable. Content the nav *covers* is
still reported.

**Measurement caveat.** This is WKWebView on macOS, so a 17px classic scrollbar eats into
the 390px surface and `clientWidth` reads 373. A real phone uses overlay scrollbars and
would read 390. Overflows within ~17px of the viewport are therefore *possibly* artefacts
and are flagged as such where they occur (M-11's 9px, the drawer's 6px). Everything else
here overflows by 50–1300px and is real on any device.

**The one fix worth making first.** Four of the blockers and several majors are the same
CSS defect: a grid track whose minimum is `auto` (min-content), so an over-wide descendant
widens every ancestor instead of being constrained. It produces a literal
`grid-template-columns: 734px` on `.dashboard-grid` and `.health-page`, 635px on
`.evaluation-layout`, and 524px on `.record-main.stack`. `minmax(0, 1fr)` on those tracks —
plus a phone breakpoint on the inner two-column grids that feed them
(`.record-meta-grid` 240px+240px, `.health-quota-figures` 344px+344px,
`.health-totals` 366px+366px) — collapses most of this report into one change.

## M-01 · App-wide horizontal scroll: the topbar is 549px wide in a 373px viewport — **BLOCKER**

- **Screen:** every admin screen (found on /submissions, confirmed on all others)
- **URL:** https://marquee.stage11.dev/submissions
- **What's wrong:** `header.topbar` lays out search + theme toggle + theme `<select>` +
  account button in a single non-wrapping row. Its `scrollWidth` is **549px** against a
  `clientWidth` of 373px, and `overflow-x` is `visible`, so it drags the whole document
  into a **176px page-level horizontal scroll**. Consequences:
  1. Every screen scrolls sideways. Content parks against the left edge with a dead grey
     gutter on the right (see `01b`), so any accidental horizontal swipe desyncs the page
     from the fixed bottom nav.
  2. The **theme toggle, theme selector, and the account button ("AC") are off-viewport at
     rest** — invisible until you discover the sideways scroll. Account is the org/role
     surface; on a phone it reads as missing, not as scrolled-away.
- **Severity:** blocker (it is the root cause of the sideways scroll on *every* screen,
  and it hides the account control)
- **Shots:** `mobile-qa-shots/01-submissions.png` (at rest — theme/account absent),
  `mobile-qa-shots/01b-submissions-scrolled-right.png` (scrolled 176px right — controls appear)

## M-23 · Submission record: one 2-column meta grid blows out the whole page to 524px — **BLOCKER**

- **Screen:** Submission record
- **URL:** https://marquee.stage11.dev/submissions/91a59ed5-5eaf-4fd4-81a9-0d5a5d17ae3e
- **What's wrong:** every card on the record is **524px wide in a 341px column**, so the
  right ~35% of the page is off-viewport and *every line of body copy is cut*. The abstract,
  the decision-history note, "Saved changes are recorded i…", the SESSION CONTENT
  sub-heading, the title `<input>` and the abstract `<textarea>` all lose their right edge.
  The text is not failing to wrap — it is wrapping correctly **to a 490px measure and then
  being clipped at 373px**, which is why it reads as sliced rather than as reflowed.
- **Exact cause — a single element:** `.record-meta-grid` computes to
  `grid-template-columns: 239.98px 240px`. It is a two-column grid with a **~240px minimum
  per track** that never collapses (a `repeat(2, minmax(240px, 1fr))`-shaped rule, not an
  `auto-fit` one), so it demands 490px in a container that has 341px. Its second column runs
  283 → 523px against a 373px viewport: **SUBMITTED, WAVE and PUBLIC STATUS are entirely
  off-screen.** That 490px then propagates straight up the tree, widening everything above it:

  `.record-meta-grid` 490 → `.record-summary` 490 → `.card-body` 522 → `section.card` 524 →
  `.record-main.stack` (single track computes to **523.98px**) → `.record-layout` (`clientWidth`
  341, `scrollWidth` 524)

  `.record-layout` itself is correct — a single 341px track. The break is entirely below it.
- **Fix shape:** collapse `.record-meta-grid` to one column at phone width — e.g.
  `repeat(auto-fit, minmax(min(100%, 240px), 1fr))` — and give `.record-main.stack` a
  `minmax(0, 1fr)` track so a too-wide descendant can never widen its ancestors again. The
  second change is the one that generalises: it is the same auto-minimum propagation behind
  M-04 (`.dashboard-grid` → 734px), M-13 (`.health-page` → 734px) and M-14
  (`.evaluation-layout` → 635px).
- **Severity:** blocker
- **Shot:** `21-submission-record.png`

## M-24 · Speaker portal: a mis-built `.portal-visually-hidden` file input adds 52px of horizontal scroll — **MAJOR**

- **Screen:** Speaker portal (as a real speaker)
- **URL:** https://marquee.stage11.dev/portal?event=aie-ny-2026&person=per_aarush-selvan
- **What's wrong:** `input[type=file].portal-visually-hidden` sets `clip: rect(0,0,0,0)` and
  `clip-path: inset(50%)` but **keeps its box**: 373 × 38px, `position: absolute; left: 51.5px`.
  Clipping hides the pixels; it does not remove the layout box, so the element's right edge
  lands at **425px** and the portal gets a 52px page-level horizontal scroll. The
  visually-hidden recipe is incomplete — it needs `width: 1px; height: 1px` (and usually
  `white-space: nowrap`) alongside the clip.
- **Why it matters more than its size:** this is the *speaker-facing* surface, i.e. the one
  page in the product that is overwhelmingly used on a phone, and it is the only thing
  making that page scroll sideways. One-line fix.
- **Severity:** major
- **Shot:** `28-speaker-portal.png`

## Non-mobile note (for whoever owns the demo harness)

Visiting `/portal?event=…&person=per_…` **switches the demo identity** to that speaker, and
every admin route then returns "Your account does not have access to this."
`?demo=organizer` does **not** switch back — only re-entering from the landing page does.

portal" / "View the agenda"), so this is a round-trip gap rather than a dead end, and it is
not a mobile issue. Noting it because it will bite the next agent that walks these routes.
